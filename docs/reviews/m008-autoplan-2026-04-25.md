Graph-aware knowledge palace RAG for agentic mentor search, temporal retrieval, and MemPalace design closure.

## Problem Statement

M005 shipped a useful first pass of MemPalace-inspired search, but it stopped at the shallow end.

Today the mentor can do three real things: inject L1 palace context into the prompt, call vector and keyword search tools, and query one knowledge-graph entity with its direct relationships. That is better than plain RAG, but it is still not a graph-native retrieval system. The palace structure is mostly metadata, not a runtime navigation surface. The knowledge graph stores relation types and age windows, but the search path does not really use them. The result is an agentic search stack that can choose tools, yet still reasons over a mostly flat corpus.

M008 exists to close that gap. The milestone should turn the palace from a labeled vector store into a navigable retrieval graph that can bridge rooms, use temporal constraints, explain why a chunk was chosen, and lift the current search stack closer to the parts of MemPalace that are actually special.

## Current-State Evidence

- `backend/app-api/src/main/java/com/zhangspaghetti/babytalk/service/SpringAiMentorProvider.java` supports `none`, `rag`, and `agentic`, but agentic mode only decides whether to register tools.
- `backend/app-api/src/main/java/com/zhangspaghetti/babytalk/palace/MemPalacePromptBuilder.java` builds L0 + L1 + L2 prompt layers, but there is no Layer 0-3 runtime stack comparable to MemPalace `layers.py`.
- `backend/app-api/src/main/java/com/zhangspaghetti/babytalk/palace/PalaceSearchService.java` is vector search with optional `wing` and `room` filters. It does not traverse graph neighbors, tunnels, or path explanations.
- `backend/app-api/src/main/java/com/zhangspaghetti/babytalk/palace/PalaceKeywordRepository.java` adds FTS keyword search and chunk reads, but hybrid ranking is still split across separate tools rather than one planner-owned ranking model.
- `backend/app-api/src/main/java/com/zhangspaghetti/babytalk/palace/PalaceToolProvider.java` exposes five tools: vector search, keyword search, read chunk, list rooms, and KG entity query. No retrieval-graph or path tool exists.
- `backend/common/src/main/java/com/zhangspaghetti/babytalk/palace/MemPalaceTaxonomy.java` and `MemPalaceMetadataEnricher.java` assign static `wing` / `room` / `hall` metadata from book title. That creates coordinates, but not navigation.
- `backend/db-migration/src/main/resources/db/migration/V14__create_knowledge_graph_tables.sql` already stores `valid_from_months`, `valid_to_months`, and relation types like `precedes`, `follows`, `part_of`, `related_to`, `causes`, and `prevents`.
- `backend/app-api/src/main/java/com/zhangspaghetti/babytalk/kg/KgQueryTool.java` only returns best-match entity details plus direct incoming and outgoing relationships. It has no time-filtered query, no invalidation flow, and no path traversal.
- `backend/app-api/src/main/java/com/zhangspaghetti/babytalk/kg/KgController.java` exposes contradiction notifications and contradiction resolution only. It does not expose graph navigation or explainability endpoints.
- `admin-web/src/pages/KnowledgeOpsPage.tsx` and `admin-web/src/lib/knowledgeOpsClient.ts` cover ingestion and KG review. There is no RAG inspection or retrieval-graph debug surface.
- No retrieval-graph-specific files were found in the Baby Talk 2 backend.
- In the local `mempalace` repo, the missing reference surfaces are explicit: `palace.py` drawers + closets, `searcher.py` hybrid retrieval, `layers.py` Layer 0-3 loading, `palace_graph.py` tunnel traversal and BFS, and `knowledge_graph.py` temporal fact windows with invalidation.

## What MemPalace Already Does That Baby Talk 2 Does Not

1. Separate verbatim storage from compact searchable pointer storage (`drawers` vs `closets`).
2. Provide a layered loading model instead of only prompt-time context injection.
3. Use hybrid retrieval and re-ranking as one retrieval path rather than separate user-visible tools.
4. Build a palace navigation graph with bridges across wings and rooms.
5. Support temporal KG semantics as query behavior, not just as stored columns.
6. Invalidate cached graph state after writes.
7. Explain navigation and bridge choices in a graph-native way.

## Goals

1. Add a real knowledge palace RAG runtime for agentic mentor search.
2. Keep the retrieval graph separate from the existing semantic KG so retrieval structure and fact structure do not get conflated.
3. Make age and temporal constraints first-class in retrieval scoring and graph traversal.
4. Upgrade agentic search from tool selection over flat indexes to graph-guided planning over rooms, entities, and evidence chunks.
5. Preserve the existing mentor chat contract and M005 user-facing behavior while improving answer quality, traceability, and multi-hop grounding.
6. Add enough operator proofing that retrieval-graph behavior can be verified and debugged, not just hoped for.

## Non-Goals

- No full MemPalace port.
- No reimplementation of MemPalace CLI, MCP server, diaries, or onboarding flows.
- No external graph database.
- No rewrite away from Spring AI, PostgreSQL, or pgvector in this milestone.
- No promise that every elegant MemPalace feature is product-relevant to Baby Talk 2.
- No canvas-first or separate-route graph dashboard. Any admin RAG UI must stay inside Knowledge Ops as an operator-first inspect surface.

## Proposed Milestone Shape

### Track A: Palace retrieval graph runtime

- Add a dedicated palace retrieval projection for traversal. Do not overload `kg_relationships` as the only graph.
- Model retrieval nodes around the palace's real retrieval surfaces: `wing`, `room`, `entity/milestone/recommendation`, and `chunk/source`.
- Model retrieval edges in four categories:
  - taxonomy edges: `wing -> room -> hall -> chunk`
  - semantic bridge edges: shared entity/topic links across rooms and books
  - temporal edges: age-window and milestone ordering signals
  - provenance edges: entity or recommendation back to supporting chunks and books
- Keep contradiction handling as a penalty or filter signal, not as an accidental traversal shortcut.

### Track B: Graph-guided agentic planner

- Introduce a planner stage before retrieval that chooses candidate wings, rooms, bridge nodes, and hop budget.
- Replace the current flat tool-choice posture with a graph-guided retrieval sequence:
  - classify query intent and child-age context
  - choose entry rooms
  - traverse bridge nodes when needed
  - retrieve evidence chunks
  - explain why those chunks won
- Add at least these retrieval-native tool surfaces or service methods:
  - palace graph traversal
  - bridge/tunnel discovery
  - path explanation
  - temporal KG query with age filter

### Track C: Temporal KG completion

- Make existing `valid_from_months` / `valid_to_months` matter at query time.
- Add explicit age-aware filtering and ranking so the same concept can resolve differently at 6 months vs 24 months.
- Add query behaviors for timeline-style relationships such as `precedes` and `follows` instead of only listing raw relations.
- Decide whether fact invalidation belongs in M008 or is deferred, but do not leave the answer implicit.

### Track D: Ingestion, cache, and proof

- Update ingestion so retrieval projection and bridge indexes refresh when new content lands.
- Add graph cache invalidation or bounded rebuild behavior so the runtime never serves stale palace topology after ingestion.
- Add operator-visible proofs for RAG behavior in both backend diagnostics and admin-web. Admin UI is baseline scope, but it remains operator-first rather than a generic graph dashboard.
- Add regression and integration proofs that the RAG changes improve retrieval quality without breaking M005 mentor chat and practice generation.

### Track E: Knowledge Ops RAG operator surface

- Extend `/knowledge-ops` from two surfaces to three: `ingestion`, `palace-rag`, and `kg-review`.
- Keep `view` / `status` / `selected` as URL truth source so RAG inspection is deep-linkable and shareable like the existing operator workbench.
- Keep the surface queue-first rather than graph-first. The left pane should open concrete operator work items, not an unbounded graph canvas.
- Baseline RAG operator queues:
  - projection queue: rebuild, stale, drift, or failed projection work items
  - bridge review: cross-room links, tunnel candidates, and suspicious bridge edges
  - trace samples: recent query traces, bad path explanations, and temporal mismatches
- Baseline RAG detail pane sections:
  - summary and actions
  - path explanation
  - local neighborhood mini-map
  - source provenance and chunks
  - rebuild or trace events
- Keep RAG permissions separate from KG review semantics: read-only inspect is one capability; rebuild, approve bridge, and rerun trace actions are separate write capabilities.
- Preserve the current admin contract: split-view, inline diagnostics, stale-state visibility, and capability-aware controls.

## Working Premises For Review

1. M005 is useful but incomplete. M008 should deepen it rather than start over.
2. Baby Talk 2 should adopt MemPalace's graph and retrieval ideas selectively, not mechanically.
3. A retrieval graph and a semantic knowledge graph are different things and should stay different things.
4. Age-aware parenting guidance is weak unless time and milestone windows affect retrieval behavior, not just stored metadata.
5. Explainability matters because graph-aware retrieval will otherwise be impossible to debug when the mentor chooses the wrong bridge.
6. A milestone that adds only graph tables but no planner behavior, no runtime traversal, and no verification would be fake completeness.

## Initial Acceptance Criteria

- Agentic mentor search can traverse palace DAG nodes beyond direct `wing` / `room` filtering.
- Multi-hop retrieval is supported with an explicit hop budget and path explanation.
- Age-aware retrieval uses `valid_from_months` / `valid_to_months` or an approved replacement in real query behavior.
- DAG projection is refreshed or invalidated after ingestion changes.
- Contradiction records can influence retrieval safety or ranking instead of being isolated in an admin-only lane.
- New graph-native service and tool surfaces are covered by focused tests.
- Existing mentor chat and practice-generation flows still pass their relevant knowledge-palace regressions.
- The final design names which MemPalace ideas were adopted, which were adapted, and which were intentionally rejected.

## Risks To Review

- Forcing the semantic KG to behave like the retrieval DAG will make both models worse.
- Multi-hop retrieval can increase latency sharply if hop expansion is not bounded and scored.
- Age windows can over-filter answers when parenting advice spans ranges instead of sharp cutoffs.
- Graph projection rebuilds can become ingestion bottlenecks if cache invalidation is hand-wavy.
- Explainability can be omitted as “nice to have,” which would make wrong-answer debugging miserable.

## Questions To Resolve In Review

- Is a minimal admin DAG diagnostic API enough for M008, or is a Knowledge Ops extension required for operability?
- Do temporal query and fact invalidation both belong in M008, or does invalidation become M008.5?

### Locked implementation shape

1. Keep the retrieval graph and semantic KG as separate models.
2. Add a palace retrieval projection that represents rooms, entities, milestones, recommendations, chunks, and provenance.
3. Add graph-guided retrieval with bounded hop budget, bridge or tunnel discovery, and path explanation.
4. Make age-aware retrieval part of both ranking and traversal eligibility, with soft preference as the default and hard gating only where the rule is explicit.
5. Tie projection rebuild or version refresh to ingestion completion so graph state cannot drift silently.
6. Extend admin-web Knowledge Ops with a third RAG operator surface rather than creating a separate graph product.

### Locked admin operator IA

- Route stays `/knowledge-ops`.
- Top-level surfaces become `Ingestion`, `Palace RAG Ops`, and `KG Review`.
- `Palace RAG Ops` stays queue-first:
  - projection queue
  - bridge review
  - trace samples
- Detail stays explanation-first, not canvas-first:
  - summary and next action
  - why this path won
  - age or temporal constraints applied
  - local neighborhood mini-map
  - supporting chunks and source books
  - rebuild or trace event history

### Locked acceptance additions

- A retrieval trace can explain why a retrieval path crossed rooms, which temporal rule affected it, and which chunks finally grounded the answer.
- `/knowledge-ops?view=palace-rag&status=...&selected=...` can deep-link to the same operator context without losing detail on reload or partial failure.
- A read-only operator can inspect the RAG queue, detail, and diagnostics without seeing mutation controls.
- A write-capable operator can rebuild projection state, approve or reject bridge proposals, and rerun traces without leaving the current queue context.
- M008 explicitly documents which MemPalace ideas were adopted, which were adapted, and which remain out of scope.

#### Section 1: Architecture

The strongest architectural call in the whole draft is also the one that must survive unchanged: the retrieval DAG and the semantic KG are not the same graph.

The bad architectural move would be to force `kg_relationships` to become the only graph and then teach the agent to walk that graph as if it were a retrieval topology. The better move is to keep semantic facts in KG, keep retrieval behavior near the current mentor seams, and only add a minimal projection when the eval proves a projection is needed.

#### Section 2: Error & Rescue

##### Error & Rescue Registry

| Failure | First visible signal | User impact | Rescue path |
|---|---|---|---|
| DAG-first build without proof | Lots of new graph code, little measured quality lift | Users barely notice improvement, team inherits complexity | Stage M008 around eval, hybrid retrieval, and trace first |
| Age windows over-filter | Correct sources disappear for cross-range questions | Mentor feels brittle or oddly narrow | Use soft boosts in v1, add hard filters only where safety demands it |
| Query trace missing | Operators cannot explain wrong evidence choice | Retrieval becomes un-debuggable | Require query trace in acceptance bar |
| Projection drift after ingestion | New knowledge fails to appear in graph behavior | Users get stale or inconsistent answers | Tie projection refresh to ingestion completion path |
| Contradiction state treated as hard truth too early | Good evidence is suppressed because admin review is incomplete | Answers get weirdly sparse or biased | Start with annotation and review-only signaling |

#### Section 3: Safety

Safety here is not about auth. It is about parenting advice quality.

The most important safety move is to make temporal and contradiction semantics visible to retrieval without pretending they are fully solved. A soft age-aware ranking model plus explicit trace is safer than a brittle hard-filter DAG that silently drops evidence.

#### Section 4: Data Flow

The preferred retrieval data flow for M008 is:

```text
user question + child age
  -> deterministic retrieval orchestrator
    -> vector candidates
    -> keyword candidates
    -> KG age / entity hints
    -> optional minimal projection lookup
  -> unified ranking + query trace
  -> prompt injection / tool response
  -> answer with source grounding
```

This is a better next step than adding a second LLM planner before the current tool-calling path is even stabilized.

#### Section 5: Code Quality

The code-quality rule for M008 is explicit over clever.

Do not add a service-side planner stage and still keep current tool-calling as the real planner. That creates two brains and no clear owner of retrieval behavior. If a planner exists at all, it should be deterministic and replace ambiguity, not compound it.

#### Section 6: Test

The current draft was right to pull proof into scope, but it was too generic.

The real proof bar is not “DAG APIs exist.” The real proof bar is that judged retrieval quality, age awareness, and source traceability improve on a curated eval without breaking current mentor and practice flows.

#### Section 7: Performance

Latency risk is concentrated in three places:

- running vector and keyword retrieval in parallel plus ranking
- optional projection lookups or bridge expansion
- extra orchestration on the hot mentor path

That is why M008 should start with deterministic hybrid ranking and only add hop expansion when the eval proves it is necessary.

#### Section 8: Observability

M008 observability should be retrieval-native:

- candidate list
- ranking reasons
- age boost or filter reasons
- projection version
- final chosen evidence

Without those five signals, every future DAG discussion turns into folklore.

#### Section 9: Rollout

The rollout sequence should be product-first, not abstraction-first:

1. Build eval set and baseline measurements.
2. Ship unified hybrid retrieval and age-aware ranking behind the existing mentor seam.
3. Add query trace and provenance.
4. Add minimal projection only where traces prove the current retriever still misses bridge cases.
5. Decide whether limited DAG traversal deserves M008.5.

#### Section 10: Long-Term Trajectory

The good six-month outcome is not “Baby Talk now has a DAG.” The good six-month outcome is “Baby Talk has measurably better grounded retrieval, and only the graph structure that earned its keep remains.”

That is the right long-term bar because it prevents architectural residue from becoming permanent product debt.

#### Section 11: Design & UX

No product UI redesign is required in the current recommended path.

There is an existing Knowledge Ops surface that could eventually host graph diagnostics, but that should follow backend proof, not lead it.

#### Failure Modes Registry

| Failure mode | Severity | Why it matters | Required mitigation |
|---|---|---|---|
| DAG-first milestone with no eval gate | Critical | Complexity outruns demonstrated value | Make eval and query trace the first gate |
| Double orchestration | Critical | Retrieval behavior becomes nondeterministic and hard to debug | One deterministic retrieval owner in v1 |
| Hard age filter too early | High | Good sources disappear | Soft boost first, explicit hard-filter approval later |
| Projection without ingestion coupling | High | Graph becomes stale | Rebuild or version projection on ingestion completion |
| Contradiction ranking too early | Medium | Admin review noise pollutes answers | Annotation before penalty, penalty before hard filter |

#### NOT in scope

- Full MemPalace parity
- Public DAG traversal API as an initial acceptance item
- Admin DAG UI as baseline scope
- Contradiction-based ranking in v1
- Cache invalidation subsystem before a real cache exists

## Roadmap

### Vision

Upgrade M005 from tool-driven flat retrieval into a graph-aware knowledge palace RAG runtime that can do four things honestly:

1. rank evidence through one deterministic hybrid retrieval owner,
2. use temporal rules and child-age context in real query behavior,
3. navigate a dedicated retrieval projection with bridges and tunnels without conflating it with the semantic KG,
4. expose enough operator proof in Knowledge Ops that wrong paths can be debugged and corrected.

### Success Criteria

- `/api/v1/mentor/chat` goes through one retrieval owner, not competing retrieval sub-owners
- direct chunk retrieval is always the floor and projection is only a ranking signal
- retrieval traces explain entry room, temporal rule, bridge/tunnel choice, winning chunks, and fallback reason
- ingestion completion refreshes or version-bumps a disposable retrieval projection, and stale/drift status is operator-visible
- `valid_from_months` / `valid_to_months` and `precedes` / `follows` change real ranking or traversal behavior
- `/api/v1/mentor/practice/generate` reuses the same retrieval / temporal / projection contract as mentor chat
- `/knowledge-ops?view=palace-rag&status=...&selected=...` works as a stable deep-linkable operator surface
- targeted backend tests, admin-web E2E, trace invariants, and judged evals pass together

### Key Risks

- graph completeness outpaces user-visible answer quality
- projection is treated as authority instead of pointer index
- age windows over-filter instead of improving relevance
- tunnel traversal turns into unbounded or weakly grounded multi-hop search
- operator UI grows into a visual toy instead of a reproducible workbench

### Proof Strategy

- prove mentor retrieval lift first on real question packs, then prove traversal and operator workflows
- collect trace artifacts for direct-hit, cross-room, and temporal-sensitive queries
- verify behavior invariants, not just happy-path answers
- keep the MemPalace mapping explicit: adopted, adapted, or deferred

##### Summary and gated actions

- Keep actions in the top-right like the existing ingestion detail pane.
- Always show disabled write actions in read-only mode, but with an explicit reason label instead of hiding the control entirely.
- Never auto-navigate away after `重建 projection`, `批准 bridge`, or `重跑 trace`. Preserve current `view/status/selected` context.

##### Why this path won

- Render as a short ordered explanation, not raw JSON.
- Required fields:
  - entry room or starting node
  - floor evidence that survived ranking
  - projection boost reason, if any
  - bridge/tunnel crossing reason, if any
  - final winning chunks
- If the answer degraded to floor-only behavior, say that plainly.

##### Temporal rules applied

- Show both positive and negative temporal reasoning.
- Operators should see not only “what matched this age” but also “what was excluded because it was too early, too late, or no longer valid”.
- Use compact status pills plus one-sentence explanations. Do not make operators read predicate names first.

##### Local neighborhood mini-map

- Keep it small, local, and collapsible.
- Maximum default scope: current node plus one hop around it.
- Provide a text fallback summary under the mini-map for accessibility and copy/paste debugging.
- This element is supportive, not the main navigation surface.

##### Supporting chunks and provenance

- Use a card stack or bordered list, not a raw blob.
- Each chunk card should show source book, wing/room, chunk index or local order, and the snippet actually used.
- If neighbor hydration added context, show that explicitly so operators understand why more text appears than the matched chunk alone.

##### Projection or trace event history

- Keep newest events first.
- Distinguish `rebuild`, `rerun`, `stale-detected`, `drift-detected`, and `review-decision` event types with both color and text labels.
- Reserve vertical space for loading states so the detail pane does not jump.

#### Interaction rules

- Preserve selected detail context on transient fetch errors, just like the current ingestion surface.
- Normalize invalid `view/status` values back to safe defaults, but keep the raw query visible in diagnostics for operator debugging.
- Show stale-state warnings inline and persist them until the next successful refresh; do not replace them with a spinner-only state.
- Loading buttons must disable during async actions.
- Retry and rebuild actions should emit immediate success/error feedback near the triggering control, not only in a global banner.

#### Accessibility and responsive rules

- Keep all primary controls at least 44x44 px.
- Do not rely on badge color alone to communicate `stale`, `failed`, `readonly`, or `mismatch` state.
- Preserve visible keyboard focus rings across surface buttons, queue row CTAs, and top-right mutation buttons.
- When the layout stacks on smaller widths, the queue must stay above the detail pane so navigation order matches reading order.
- Avoid horizontal scroll in queue rows. Long labels should wrap or truncate with accessible tooltip text.

#### Motion and performance rules

- Use only short transform/opacity transitions in the 150-300 ms range.
- Respect reduced-motion preferences for the mini-map and any row-to-detail emphasis effect.
- Keep queue rows lightweight. Do not render a live graph preview in every row.
- Reserve detail-pane skeleton height during async loads to prevent content jumping.

#### Copy rules

- Prefer operator language over system jargon. Example: `为什么这条路径胜出` is better than `ranking explanation payload`.
- When a path falls back to floor retrieval, say `projection 未参与，本次按直接证据排序` instead of implying failure.
- When a bridge/tunnel is inferred rather than confirmed, state that plainly in the detail header.
