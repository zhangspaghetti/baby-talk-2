# 未提交文件审核与分阶段提交设计

- 日期：2026-05-30
- 目标：对当前未提交文件进行可追溯审核，并按规范化 git 工作流完成分阶段提交
- 适用范围：当前工作区全部已跟踪与未跟踪改动

## 1. 背景

当前工作区存在大量跨目录改动（docs、mobile、scripts、配置与新增目录）。
如果直接一次性提交，会带来以下问题：

1. 审查负担过高，难以定位行为性变更。
2. 回滚粒度过粗，出现问题时代价高。
3. 历史可读性下降，不利于后续 cherry-pick 与追责。

本设计采用先基线归档、再功能拆分的提交策略，保证提交历史可读、可审、可回滚。

## 2. 目标与非目标

### 2.1 目标

1. 对所有未提交文件建立清晰审核边界。
2. 通过分阶段提交隔离噪音与功能改动。
3. 每个提交保持单一意图，并附可验证证据。

### 2.2 非目标

1. 本设计不定义业务功能实现细节。
2. 本设计不替代代码审查结论，仅规范提交流程。
3. 本设计不强制新增测试框架，仅复用现有验证命令。

## 3. 提交架构（方案 C）

### 3.1 Stage 1：基线归档提交

仅允许进入本阶段的变更：

1. 文档索引、记录性文本、报告归档。
2. 不改变运行时语义的整理性改动。

禁止进入本阶段的变更：

1. 代码逻辑变化。
2. 配置行为变化。
3. 文件删除或迁移导致的运行路径变化。

### 3.2 Stage 2：功能提交集

按能力拆分多个提交：

1. 组件与主题体系。
2. 页面与交互行为。
3. 测试与集成。
4. 工具脚本与运行配置。

约束：每个提交只表达一个能力意图，提交间可独立回滚。

### 3.3 Stage 3：收尾提交（可选）

用于处理在 Stage 1/2 后发现的轻量遗漏：

1. 小范围文案修正。
2. 注释与说明对齐。

若无必要，跳过该阶段。

## 4. 文件分组规则

### 4.1 Stage 1 判定规则

1. 仅影响可读性、归档性、记录性。
2. 可证明对运行行为零影响。
3. 典型对象：文档索引、报告产物文件。

### 4.2 Stage 2 判定规则

1. 所有 Dart 代码改动默认进入 Stage 2。
2. 所有测试改动默认进入 Stage 2。
3. 脚本与配置变更默认进入 Stage 2。
4. 删除文件一律进入 Stage 2 并附迁移说明。

### 4.3 冲突与兜底规则

1. 同一文件同时包含格式与行为变更，归 Stage 2。
2. 无法判断时采用保守策略，归 Stage 2。
3. 跨目录但同一能力的改动，不按目录拆，按能力归组。

## 5. 审核与验证流程

每个提交前执行以下检查：

1. 边界检查：是否单一意图。
2. 风险检查：是否混入无关文件。
3. 证据检查：是否有对应测试或日志。
4. 回滚检查：是否可独立回退。

建议验证策略：

1. Stage 1：以静态检查与文件清单复核为主。
2. Stage 2：按能力执行最小回归验证（优先已有测试命令）。
3. Stage 3：仅做轻量回归或 smoke 检查。

## 6. 提交消息规范

采用约定式提交格式：

1. 格式：type(scope): summary
2. type 建议：docs、feat、fix、refactor、test、chore
3. summary 规则：
   - 动词开头
   - 描述可验证结果
   - 避免情绪性措辞

涉及删除或迁移时，在提交正文补充：

1. 迁移说明
2. 回滚提示

## 7. 执行顺序

1. 生成 Stage 1 候选文件清单并确认。
2. 提交 Stage 1。
3. 逐个执行 Stage 2 提交并逐个验证。
4. 视情况执行 Stage 3 收尾提交。
5. 输出最终提交序列与风险备注。

## 8. 风险与缓解

1. 风险：分组不当导致提交耦合。
   - 缓解：提交前强制执行边界检查。

2. 风险：遗漏未跟踪关键文件。
   - 缓解：每阶段前后对比 git status 清单。

3. 风险：提交信息不一致影响历史可读性。
   - 缓解：统一使用 type(scope): summary 模板。

## 9. 验收标准

1. 提交历史可清晰映射到 Stage 1/2/3。
2. 任一 Stage 2 提交可独立回滚。
3. 每个提交都有对应验证证据或检查记录。
4. 最终工作区仅保留明确计划内未提交项。
