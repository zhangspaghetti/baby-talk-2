# M007 Milestone Plan

## Title

Helm-first split deployment, gateway front door, persistence stack migration, and collaborative onboarding docs.

## Request Snapshot

The user requested M007 to do five concrete things:

1. Do not deploy PostgreSQL + pgvector, Redis, and app workloads together. Deploy infrastructure separately.
2. Use Helm charts for both local and production environments. Do not use docker compose as the supported deploy path.
3. Replace direct JdbcTemplate runtime usage with MyBatisPlus, and add Druid plus Hutool.
4. Add a Gateway service that becomes the only backend entry point, including auth/authz and route forwarding.
5. Use the doc-coauthoring workflow to produce a collaborative README. It must include Getting Started and must not be only a list of startup scripts.

## Problem Statement

Current repo truth is split in the worst possible place.

Infrastructure lifecycle, app lifecycle, public ingress, and developer onboarding are all telling different stories. `docker-compose.yml` boots `postgres`, `minio`, `db-migration`, `app-api`, `admin-api`, and `admin-web` together. The root README and CONTRIBUTING are already front-door oriented, but they still carry compose-shaped backend truth and admin-demo-first onboarding. Helm exists, but it is not the single day-one local truth. Backend ingress is split across `app-api`, `admin-api`, `admin-web` proxy behavior, and Kubernetes ingress. Runtime persistence is JdbcTemplate-heavy across `common`, `app-api`, and `admin-api`.

M007 exists to make deployment topology, service boundaries, persistence patterns, and onboarding docs tell one consistent story.

## Current-State Evidence

- `docker-compose.yml` boots `postgres`, `minio`, `db-migration`, `app-api`, `admin-api`, and `admin-web` as one local bundle.
- `README.md` and `CONTRIBUTING.md` still teach docker compose in the local backend path and reuse that truth in release/debug ladders.
- Helm already exists under `deploy/helm/babytalk`, with local values and production values, but local day-one usage is not authoritative.
- MinIO is a live shared dependency in compose, Helm secret/config surfaces, and ingestion runtime.
- Redis is named in the user request and older architecture notes, but it is not currently proven as a live runtime dependency in the checked-in repo. The approval gate now locks Redis in as an explicit M007 target dependency, not a current-state assumption.
- `backend/pom.xml` currently declares four modules only: `common`, `app-api`, `admin-api`, and `db-migration`.
- Backend runtime today is Spring Boot 3.4.4 + Java 17 + `spring-boot-starter-jdbc`.
- Runtime repositories and read models are heavily built on direct `JdbcTemplate` across admin auth, RBAC, overview, mentor audit, distribution, knowledge ops, ingestion, share, mentor, auth, and caregiver flows.
- No source-level gateway module or Spring Cloud Gateway surface exists.
- The root README is already a strong front door, but it is still anchored to current admin demo and compose-era backend assumptions rather than an M007-wide collaborative onboarding contract.

## Goals

1. Separate infrastructure lifecycle from app lifecycle for both local and production deployments.
2. Make Helm the only supported deploy path for both local and production environments.
3. Introduce a Gateway service as the only public backend ingress and auth/routing choke point.
4. Migrate runtime persistence from direct JdbcTemplate repositories to MyBatisPlus-backed repository adapters, with Druid and Hutool as standard backend infrastructure.
5. Replace script-first onboarding docs with a collaborative README produced through the doc-coauthoring workflow, including at minimum Getting Started.

## Non-Goals

- No UI redesign of admin-web or mobile surfaces.
- No service mesh rollout.
- No multi-cluster program.
- No domain rewrite of mentor, distribution, knowledge, or auth product semantics beyond deploy boundary, gateway boundary, and persistence-adapter migration.
- No removal of Flyway/db-migration as schema owner in this milestone.

## Proposed Milestone Shape

### Track A: Deploy topology

- Split infrastructure into a dedicated release boundary: PostgreSQL + pgvector, MinIO/object storage, and Redis as an explicit M007 target dependency.
- Split app runtime into a separate release boundary: `gateway`, `app-api`, `admin-api`, `admin-web`, `db-migration`.
- Local development moves from docker compose to Helm on a local Kubernetes cluster.
- Official first local baseline: `kind + helm` on top of Docker Desktop for Windows parity, while keeping the truth expressed in Helm rather than compose.

### Track B: Backend edge and routing

- Add a new backend module: `gateway`.
- Public clients talk only to `gateway`.
- `app-api` and `admin-api` become cluster-internal services.
- Gateway owns authentication handoff, authorization prechecks where appropriate, route forwarding, and consistent error/observability envelopes.
- `admin-web` proxy and ingress documentation must be simplified so the backend front door is unambiguous.

### Track C: Persistence stack migration

- Add MyBatisPlus, Druid, and Hutool to the backend parent/module stack.
- Keep business semantics in services. Move SQL behind repository adapters and mapper interfaces.
- Treat current JdbcTemplate repositories/read models across `common`, `app-api`, and `admin-api` as repo-wide M007 migration targets, executed in waves rather than one blind mechanical cut.
- Tests may still use JdbcTemplate for setup/assertion where that is cheaper, but runtime code should stop growing new direct JdbcTemplate seams.

### Track D: Developer onboarding and documentation

- Use the doc-coauthoring workflow for the root README deliverable.
- README must be collaborative, task-first, and fresh-reader-safe. Not just a pile of wrapper commands.
- Minimum sections: `Getting Started`, architecture map, local prerequisites, local deploy/verify path, troubleshooting, module boundaries, common workflows, release/deploy entry points.
- Apply doc-coauthoring end to end:
  - Stage 1: gather context from current README, CONTRIBUTING, runbooks, scripts, and verification ladders.
  - Stage 2: draft README section by section around real reader tasks.
  - Stage 3: reader-test the README against a fresh reader with no repo history.
- `CONTRIBUTING.md`, runbooks, and verifiers must align with the new Helm-first truth.

## Working Premises For Review

1. Infrastructure and app lifecycles must be independently deployable in both local and production environments.
2. Helm should replace docker compose as the authoritative local and production deploy surface, not just production packaging.
3. A dedicated gateway is the right place for the public backend trust boundary, instead of leaving ingress and auth split across `admin-web`, `app-api`, `admin-api`, and ingress resources.
4. MyBatisPlus + Druid + Hutool is an acceptable migration cost for this codebase and should be done as a repository-adapter migration, not a service-layer rewrite.
5. The README is part of the product surface for developers. It must be rewritten as a collaborative document with `Getting Started` as a first-class deliverable, not treated as post-implementation polish.
6. To complete the infra/app split honestly, every live shared infra dependency still mixed into the current compose or Helm path must be reviewed inside the same milestone rather than left as hidden coupling. MinIO clearly qualifies. Redis is now an explicit M007 target dependency and must be reflected consistently in topology, Helm values, verification, and docs.

## Initial Acceptance Criteria

- No supported local or production golden path depends on docker compose.
- Helm charts and values support separate infrastructure and app release units for local and production.
- A new `gateway` module/service exists and is the only public backend entry.
- `app-api` and `admin-api` are internal-only in deploy truth.
- Runtime persistence code is migrated off direct JdbcTemplate in `common`, `app-api`, and `admin-api`, with MyBatisPlus-backed adapters as the supported runtime path and JdbcTemplate limited to test/setup usage where still justified.
- Druid and Hutool are wired and documented.
- Root README is rewritten via the doc-coauthoring workflow and includes `Getting Started`.
- `README.md`, `CONTRIBUTING.md`, runbooks, CI/deploy scripts, and verifiers all point to the same Helm-first truth.

## Risks To Review

- Local Helm on Windows can fail if the cluster/tooling choice stays vague.
- Gateway introduction can accidentally duplicate auth logic instead of centralizing it.
- Repo-wide persistence migration can sprawl if read models, write models, and test fixtures move without an explicit batch plan, inventory, and rollback criteria.
- README rewrite will fail if it is treated as final-pass polish instead of an in-scope milestone deliverable.

## Questions To Resolve In Review

- Which local Kubernetes baseline is official: `kind`, `k3d`, or something else?
- Does `admin-web` continue proxying only to `gateway`, or does it keep direct `admin-api` dev exceptions?
- Which parts of existing Helm/verify tooling can be adapted versus replaced?
- Which JdbcTemplate runtime surfaces are first-wave mandatory for M007 done-state, and which can be temporarily wrapped behind adapters?

#### Section 1: Architecture

I examined the repo's current module graph, proxy graph, Helm surfaces, and release proof surfaces.

The plan is viable only as a wave-ordered platform reframe, not as a parallel rewrite. The right architecture move is additive first, subtractive second:

```text
external client
    |
    v
 gateway
  |    \
  |     \__ edge policy, token validation/propagation, rate limiting, route policy
  |
  +----> app-api     (internal)
  |
  +----> admin-api   (internal)
  |
admin-web ----------> gateway

db-migration -------> postgres/pgvector
ingestion ----------> minio + postgres/pgvector
```

Hard architectural calls for M007:

- Add `gateway` as a new backend module rather than hiding gateway behavior inside `admin-web` or ingress snippets.
- Keep `common` thin and reuse `JwtTokenService` as a shared primitive instead of inventing a new token stack.
- Keep service-layer authorization inside `app-api` and `admin-api`. Gateway owns edge policy, not business authorization truth.
- Local and production truth must both reduce to the same Helm model. One local cluster baseline. One gateway front door. One internal-service rule.

#### Section 3: Security

I examined the current split between admin-web proxying, JWT primitives, and separate admin/consumer token issuers.

The security mistake to avoid is moving all security semantics into gateway. That would create duplicated policy and new bypass risk. M007 security should instead do four explicit things:

- Gateway validates edge tokens, forwards only trusted identity context, and enforces route-level policy.
- `app-api` and `admin-api` remain responsible for domain authorization and destructive-action invariants.
- Helm truth must remove public ingress to internal services so the gateway is a real choke point.
- Admin-web dev/prod proxying must point at gateway after cutover, not keep a silent direct `admin-api` escape hatch by default.

#### Section 4: Data Flow

The critical new data flow is not business-domain data. It is request routing truth.

M007 must explicitly handle four path variants for every routed request:

- Happy path: valid token, route exists, upstream healthy, response returned.
- Missing/empty auth path: request rejected at gateway with a named contract error.
- Upstream error path: gateway emits named 5xx/timeout envelope with route diagnostics.
- Partial-cutover path: legacy caller or direct proxy path still exists while migration is underway.

If the partial-cutover path stays implicit, the milestone will quietly retain two backend front doors.

#### Section 5: Code Quality

The code-quality win is not "use more frameworks." The win is consistency.

M007 should enforce these quality rules:

- No new runtime repository or read model should be introduced with direct JdbcTemplate once the migration starts.
- MyBatisPlus must stay behind repository adapters and mapper interfaces.
- Druid stays an infrastructure concern, not a business-logic abstraction surface.
- Hutool should be treated as a targeted utility library, not a reason to spread convenience helpers through every service.
- The repo should never end M007 with three equally blessed persistence styles.

#### Section 6: Test

Current proof tooling is strong, but it is still aimed at compose-first local truth.

M007 needs a new test spine:

- local Helm bootstrap proof
- gateway route and auth contract tests
- internal-only ingress proof for `app-api` and `admin-api`
- migration-slice repository tests proving MyBatisPlus adapters preserve behavior
- docs proof that README/CONTRIBUTING/runbooks point to the same Helm-first path

Compose-era proof can remain temporarily during cutover, but it cannot be the final acceptance truth for M007 done-state.

#### Section 7: Performance

Two performance risks matter here.

First, gateway adds a hop. That is acceptable only if gateway stays thin and observable. Second, some current read models are large JdbcTemplate surfaces. A careless mapper migration can regress query behavior while claiming architectural improvement. M007 should therefore bias toward one representative bounded-slice migration first, with slow-query visibility from Druid, before sweeping every repository mechanically.

#### Section 8: Observability

Observability is part of the milestone, not follow-up polish.

M007 needs at least three new observability surfaces:

- gateway: request count, upstream latency, auth failure count, route miss count, upstream failure taxonomy
- local Helm gold path: `tthw_seconds`, `first_failure_stage`, `likely_cause`, `next_action`
- migration slice: slow-query visibility, pool pressure, and route-level error rates during cutover

Runbooks must explain what to do when those signals go red.

#### Section 9: Deployment

This is the most important section of the whole review.

The milestone only works if deployment is staged in waves:

1. Lock one local Kubernetes baseline and one Helm gold path.
2. Split infra and app release truth, keeping compose only as an explicitly deprecated bridge if still needed during parity work.
3. Introduce gateway and move public/backend ingress through it.
4. Migrate one representative persistence slice and freeze new JdbcTemplate growth.
5. Align README, CONTRIBUTING, runbooks, and proof tooling with the new truth.

Trying to do all five in parallel is how M007 becomes a rewrite with no reliable finish line.

#### Section 10: Long-Term Trajectory

The six-month regret scenario is clear.

If M007 finishes with compose still easier locally, direct service access still common in tests or dev proxies, and two persistence styles still growing, then the milestone will have spent a lot of engineering time without changing team behavior. The good version of M007 creates a rulebook for the next year: one deploy story, one backend front door, one repository direction, one onboarding story.

#### Section 11: Design & UX

No product UI redesign is needed here.

The design surface is operator and developer interaction quality: command UX, error wording, docs flow, and whether the new path feels obvious. The current README already proves the repo can write good front-door docs. M007 should evolve that strength into a broader collaborative platform onboarding doc instead of pretending the repo has no doc structure today.

`codex-cli` remains unavailable, so the engineering review also runs in `subagent-only` mode.

Top engineering findings from the independent review, validated against nearby repo anchors:

1. Gateway cannot own all auth and authz semantics because `app-api` and `admin-api` already enforce different token and route contracts.
2. The repo currently has multiple real backend front doors: direct `admin-api` proxying in `admin-web`, direct `app-api` production ingress, and direct host-port exposure in compose.
3. Helm-first local is not yet an executable engineering contract because current release verification still treats compose runtime truth as primary.
4. `db-migration` is currently owned as a same-chart hook and compose-first schema owner, so infra/app split needs an explicit compatibility and rollback matrix.
5. Gateway migration must cover optional-auth, public, consumer-auth, admin-auth, and streaming paths, not just nominal authenticated CRUD.
6. MyBatisPlus + Druid + Hutool is large enough that repo-wide replacement inside one milestone is a deliberate scope expansion and needs explicit batching, inventory, and rollback rules.

#### Architecture Review

The module move is sound if implemented as a sibling addition, not a policy vacuum:

```text
Wave 1: local Helm truth + baseline ADR + route/auth matrix
Wave 2: infra/app release split + schema compatibility matrix
Wave 3: thin gateway on admin surface + proxy cutover
Wave 4: gateway on consumer/public surface + direct front-door closure
Wave 5: freeze new JdbcTemplate + repo-wide replacement executed in sequenced batches
```

Engineering architecture requirements:

- `gateway` is a new backend module under the existing reactor, not a hidden NGINX rewrite.
- `app-api` and `admin-api` remain internal services in the target topology.
- `admin-web` dev and prod proxy paths must both converge on gateway.
- `db-migration` ownership, execution timing, and rollback semantics must be explicit before the infra/app split is declared done.
- Redis is an explicit target dependency and must shape the release topology, local values, and verification path intentionally rather than by historical accident.

#### Code Quality Review

Engineering quality for M007 should be enforced as guardrails, not vibes:

- no new runtime `JdbcTemplate` seams after the freeze point
- MyBatisPlus introduced only behind repository adapters and mapper interfaces
- Druid configuration stays at datasource and observability boundaries
- Hutool usage stays narrow and justified
- gateway code stays thin enough that route policy, identity validation, and observability are easy to reason about
- repo-wide migration is user-selected scope and therefore must be tracked by inventory, batch ownership, and rollback criteria instead of a single giant cutover

The main anti-pattern to avoid is parallel architectural drift: old persistence style still growing while new framework surfaces are introduced alongside a gateway rewrite.

#### Embedded Engineering Test Plan

##### Objective

Prove that M007 changes platform truth instead of only adding new components.

The engineering acceptance bar is:

- one local Helm-first bootstrap path is executable end to end
- gateway becomes the only intended backend entry path after cutover
- infra/app release split preserves schema compatibility and rollback safety
- repo-wide runtime persistence migration completes without collapsing rollback safety or observability

##### Non-Goals

- one-shot blind replacement of every JdbcTemplate seam without inventory or batch gates
- deleting compose before Helm parity is proven
- moving business-domain authorization into gateway
- treating Redis as current-state truth rather than an intentional M007 target dependency

##### Preconditions

These artifacts must exist before implementation is considered ready for broad execution:

1. Local Kubernetes baseline ADR locking `kind + Docker Desktop + Helm + kubectl` as the first supported path.
2. Route and auth matrix covering public, optional-auth, consumer-auth, admin-auth, and streaming paths.
3. Schema compatibility matrix covering gateway, app-api, admin-api, db-migration, and schema version combinations.
4. Public/internal exposure map for gateway, app-api, admin-api, admin-web, db-migration, Postgres, MinIO, and Redis.
5. JdbcTemplate inventory grouped by runtime auth, read model, write model, infra bean, and test fixture.
6. Repo-wide migration batch plan showing ownership, order, and rollback criteria for each batch.

##### Verification Waves

###### Wave 1: Local Helm Truth

Goal: replace compose-first local truth with one supported Helm-first path.

Checks:

- preflight verifies required tools, cluster baseline, storage class assumptions, ingress/host assumptions, and image availability
- chart render proves gateway/internal exposure defaults are coherent
- local install brings up db-migration, app-api, admin-api, admin-web, Redis, and required infra in the intended order
- live smoke validates gateway health, admin-web landing, and at least one consumer and one admin backend path
- docs proof confirms README, CONTRIBUTING, and runbooks all point to the same local path

###### Wave 2: Infra/App Release Split

Goal: prove separate release ownership without breaking runtime compatibility.

Checks:

- infra release and app release can be rendered, installed, upgraded, and rolled back independently within the supported matrix
- db-migration owner and execution point are explicit
- expand/contract schema sequence is documented and tested
- partial deploy tests prove allowed combinations and reject unsupported combinations loudly

Required scenarios:

- old gateway/services on new schema
- new gateway/services on old-but-compatible schema
- rollback from failed app release without infra rollback
- rollback from failed migration before public traffic cutover

###### Wave 3: Gateway Admin Cutover

Goal: prove thin-edge gateway behavior on the simpler admin surface first.

Checks:

- admin-web dev proxy and production proxy route through gateway
- admin login, refresh, logout, and one authenticated read path succeed through gateway
- direct admin-api exposure is absent from intended public entrypoints
- header trust contract is enforced and spoofed forwarding headers are stripped/rebuilt
- error envelope and route diagnostics are observable on auth and upstream failures

Required scenarios:

- missing token
- malformed token
- expired token
- upstream timeout
- upstream 5xx

###### Wave 4: Gateway Consumer/Public Cutover

Goal: preserve current public and optional-auth semantics while closing direct-service front doors.

Checks:

- public routes remain public through gateway
- optional-auth routes preserve anonymous success and authenticated enrichment behavior
- consumer-auth routes continue to require valid consumer tokens
- direct public ingress to app-api is removed from the final target topology
- mixed-version tests prove safe rollout order during cutover

Required scenarios:

- public route with no bearer token
- public route with malformed bearer token
- optional-auth route with and without bearer token
- consumer-auth route with admin token rejected
- consumer-auth route with consumer token accepted
- streaming path routed through gateway without regression

###### Wave 5: Repo-Wide Persistence Migration

Goal: complete the user-selected full replacement without losing control of risk.

Checks:

- no new runtime JdbcTemplate usage lands after the freeze point
- repo-wide inventory is drained batch by batch with named owners and rollback points
- MyBatisPlus mapper behavior matches previous repository behavior for each migration batch
- Druid datasource and pool metrics are visible in local and production-oriented configs
- slow-query visibility exists for each migrated batch
- final runtime audit proves no supported runtime path in `common`, `app-api`, or `admin-api` still depends on direct JdbcTemplate

Required batch families:

- admin read-models
- admin auth/session
- common ingestion and shared infra repositories
- app-api consumer/auth/share/mentor flows

##### Test Matrix

| Area | Test type | Minimum proof |
|---|---|---|
| Helm baseline | script + live smoke | successful local cluster bootstrap and route smoke |
| Route/auth contract | integration tests | matrix covering admin, consumer, public, optional-auth, streaming |
| Exposure control | chart render + runtime check | only gateway and intended public web surface exposed |
| Mixed-version rollout | integration or scripted environment tests | supported upgrade and rollback combinations pass |
| Schema compatibility | migration tests + rollout checks | allowed combinations documented and enforced |
| Repo-wide persistence migration | repository and batch-parity tests | each batch matches prior behavior and final runtime audit is clean |
| Docs truth | reader-path proof | README, CONTRIBUTING, runbook, and wrapper commands agree |

##### Exit Criteria

M007 engineering proof is acceptable only when all of the following are true:

1. A fresh developer can complete the supported local Helm path without compose as the primary instruction.
2. Gateway is the only intended backend entrypoint in the final target topology.
3. Partial deploy and rollback behavior are described by a compatibility matrix and covered by at least one executable proof path.
4. Admin and consumer token semantics are preserved across gateway cutover.
5. All supported runtime direct JdbcTemplate usage across `common`, `app-api`, and `admin-api` is removed or explicitly moved out of runtime paths.
6. README, CONTRIBUTING, verifiers, and runbooks describe the same truth.

#### Performance Review

Three performance concerns are active:

- gateway hop and route instrumentation overhead
- streaming/admin live-path behavior through the new edge
- query regressions when repo-wide `JdbcTemplate` batches move behind MyBatisPlus + Druid

The mitigation is bounded rollout plus visible latency and slow-query signals, not a promise that framework change is automatically faster.

#### Worktree Parallelization Strategy

Safe parallelization exists, but it is conditional:

| Workstream | Can start when | Must not finish before |
|---|---|---|
| A. Local Helm baseline and local values | now | route/auth matrix exists |
| B. Route/auth matrix and gateway thin-edge ADR | now | admin proxy cutover |
| C. Infra/app release split and schema compatibility matrix | after A starts | public cutover |
| D. Gateway admin cutover | after B and C are real | consumer/public cutover |
| E. Repo-wide persistence inventory, batch plan, and freeze rule | now | final runtime replacement completion |
| F. Docs/verifier alignment | after A-D truth is stable | final README/prose lock |

This is not six fully parallel worktrees. It is six coordinated tracks with explicit dependency edges.

#### Engineering Defer List

- gateway-owned business authz or RBAC semantics
- final compose removal before Helm parity is executable
- one-shot unbatched persistence cutover without rollback checkpoints
- multiple supported local cluster baselines
