# Duolingo-like Care Path Three-Milestone Roadmap Design

- **Date:** 2026-07-23
- **Status:** Approved design
- **Target repository:** `baby-talk-2`
- **Target branch:** `Develop`
- **Baseline commit:** `f8fa0ec70191bc00dd3eed3f6059a87bcd5a8648`
- **Source bundle:** `Develop-20260723.bundle`
- **Milestones:** M1 First Care-turn Onboarding, M2 Custom Scene Mobile Loop, M3 Care Path Visual Cohesion

## 1. Purpose

This design defines the next three independently releasable milestones for Baby Talk after completion of the local CI and reliable private custom-scene backend work.

The roadmap applies the approved Duolingo-like information architecture without adopting Duolingo's learning-product identity or reward economy. Baby Talk remains a real-time bilingual parenting companion for Chinese parents of children aged 0–3. Its primary value is to give a parent a complete, playable, directly speakable family-English utterance tied to the current care action, then continue appropriately when the child or situation changes.

The three milestones are:

1. **M1 — First Care-turn Onboarding**: replace the legacy onboarding phrase loop with one real care turn, a real Garden trace, and optional account saving after first value.
2. **M2 — Custom Scene Mobile Loop**: connect the existing private custom-scene backend to Today and Scene, preserve login continuation, hand the approved output into the formal care-turn path, and provide non-persistent real-time TTS audio.
3. **M3 — Care Path Visual Cohesion**: unify the visual and interaction language of the stable main paths without changing the four-tab information architecture or business contracts.

Each milestone MUST remain runnable, testable, independently acceptable, and independently releasable.

## 2. Product direction and hard boundaries

### 2.1 Core product loop

All three milestones MUST preserve one formal product loop:

```text
real care context
→ care moment
→ current speakable utterance
→ playable audio
→ parent says it
→ canonical child reaction
→ next support utterance
→ Garden trace
→ Today continuity
```

Onboarding, generated custom scenes, and ordinary catalog scenes MUST NOT maintain parallel phrase, reaction, event, Garden, or identity systems.

### 2.2 Duolingo-like means structure, not identity

The roadmap MAY borrow:

- a clear primary path;
- one dominant current action;
- incremental disclosure;
- immediate state feedback;
- stable navigation;
- visible long-term continuity.

The roadmap MUST NOT introduce or prebuild:

- XP or points;
- coins or a spendable currency;
- leaderboards or leagues;
- quests or task lists;
- hard streaks or loss-based reminders;
- right/wrong scoring;
- child-performance grading;
- lesson, exercise, course, or completion framing.

Garden records real family-English moments and continuity. It is not a reward system.

Points, coins, streaks, leaderboards, and related engagement mechanics remain a possible later research topic. They are not permanently prohibited, but they require a separate product design and safety review proving that they support real care rather than turn care into a task. They are outside all three milestones.

### 2.3 Shared implementation foundation

The milestones SHOULD reuse the current formal layers, including:

- `mobile/lib/features/care_path/data/repositories/care_path_repository.dart`
- `mobile/lib/features/care_path/presentation/care_path_notifier.dart`
- `mobile/lib/features/care_path/domain/models/care_path_models.dart`
- `mobile/lib/features/practice/data/repositories/practice_repository.dart`
- `mobile/lib/features/practice/data/repositories/garden_growth_repository.dart`
- `mobile/lib/features/practice/domain/models/interaction_event_payload.dart`
- `mobile/lib/features/account/data/repositories/account_repository.dart`
- `mobile/lib/features/account/presentation/account_notifier.dart`
- GoRouter, Riverpod, Isar, and the current authenticated API client.

New shared foundations MUST be narrowly limited to:

- authentication continuation and pending-intent restoration;
- a generated-care-moment adapter into the formal care-turn path;
- a unified audio playback abstraction supporting packaged assets and generated bytes;
- shared loading, error, unknown-outcome, and result semantics used by the relevant paths.

The implementation MUST NOT create a second onboarding phrase engine, custom-scene session engine, reaction enum, Garden write path, or user-session store.

## 3. Current baseline at `f8fa0ec`

### 3.1 Legacy onboarding remains active

The current onboarding feature contains a separate session model and phrase loop under:

```text
mobile/lib/features/onboarding/
```

Notable legacy pieces include:

- `onboarding_session_notifier.dart`
- `scene_phrase_service.dart`
- onboarding-specific `BabyReaction`
- onboarding-specific `PracticeRecord`
- separate practice, completion, and Garden-welcome screens
- route paths under `/onboarding/*`.

`OnboardingRepository.completeOnboarding()` resolves a configured starter seed rather than necessarily persisting the exact moment and phrase the user just used. This breaks first-session continuity.

### 3.2 Formal Care Path already supports the core reaction loop

`CarePathRepository` currently supports:

- loading a current turn;
- starting a selected moment;
- recording a canonical `BabyReactionType` through `PracticeRepository`;
- resolving the next support utterance;
- loading the latest Garden impact.

`CarePathNotifier` already coordinates the presentation state for this path.

M1 MUST reuse and harden this path instead of reimplementing it.

### 3.3 Four-tab IA and one-turn surface exist

The product already uses the approved bottom navigation concepts:

```text
Today / Scene / Garden / My
```

Today, the Scene catalog, and the current practice/one-turn surface are present. M3 therefore does not redesign the information architecture.

### 3.4 Mobile has no custom-scene discovery integration

The current mobile tree does not expose a custom-scene request to `POST /api/v1/practice/discovery` and has no mobile domain mapping from approved generated content into the Care Path.

M2 is a new end-to-end mobile vertical slice rather than a visual button hookup.

### 3.5 Current audio abstraction is asset-only

`mobile/lib/features/practice/presentation/practice_audio_controller.dart` currently plays packaged assets. M2 must evolve the abstraction to also play generated audio bytes while preserving the existing seed-audio path.

### 3.6 Current `AuthScreen` is not a continuation-capable session flow

The existing auth screen does not by itself provide the complete pending-intent, session-persistence, return, and resume contract required by M1 and M2. The reusable account/session source of truth remains `AccountRepository` and `AccountNotifier`.


## 5. M1 — First Care-turn Onboarding

### 5.1 Outcome

A new user completes one real care turn before entering Today:

```text
welcome
→ age range
→ common care scenes
→ parent support goal
→ current care moment
→ first utterance
→ listen
→ “I said it”
→ canonical child reaction
→ next support utterance
→ first real Garden trace
→ optional account saving
→ Today continuity
```

The success criterion is continuity: after onboarding, Today MUST reflect the same real care context and persisted interaction, not restart from an unrelated configured seed.

### 5.2 Account timing

Account creation or login MUST occur only after the first utterance, reaction, next support, and Garden trace have delivered first value.

The account invitation MUST be optional:

```text
save to an account
or
continue locally
```

Choosing local mode completes onboarding without repeated blocking prompts. Account saving remains available later from My.

### 5.3 Onboarding state model

M1 SHOULD introduce a dedicated onboarding flow model responsible only for onboarding progress and selections. It does not own phrase generation or reaction persistence.

The flow should represent at least:

```text
welcome
age
scene preferences
support goal
current moment
care turn
reaction
next support
Garden trace
account invitation
complete
```

Persist the minimum resumable snapshot rather than widget state. The snapshot should include the selected age bucket, scene preferences, support goal, selected moment identity, current flow phase, event/reconciliation identity where required, and completion state.

### 5.4 Age and profile scope

Use low-precision age buckets rather than requiring a birth date:

- 0–6 months;
- 7–12 months;
- 1–2 years;
- 2–3 years.

Age may control content suitability and support detail. It MUST NOT create a learning level.

A default child display name such as `宝宝` is acceptable for the first local experience. Personal naming is not a prerequisite to first value.

### 5.5 Scene preferences and current moment

Scene preferences represent recurring family contexts. The current moment represents what is happening now. The flow MUST distinguish them.

Example recurring contexts include waking, diapering, dressing, feeding, bathing, going out, playing, and bedtime.

The current-moment choice MUST resolve to an existing `spaceId` and `activityId` and call the formal `CarePathRepository.startMoment()` path. If the exact seed is unavailable, the system may choose a safe starter in the same care space. M1 MUST NOT invoke Custom Scene generation.

### 5.6 First utterance surface

The first utterance surface MUST display:

- complete English parent speech;
- natural Chinese meaning support;
- short action timing;
- “听一下” audio control;
- “我说了” primary action.

It MUST NOT display lesson position, progress fractions, scores, correctness, or completion framing.

M1 uses existing packaged audio assets. Audio failure is recoverable and MUST NOT block the user from saying the sentence or continuing the care turn.

### 5.7 Canonical reaction and formal event write

After “我说了”, the UI presents the canonical five-value reaction contract:

```text
cooperating
hesitant
resisting
no_response
other
```

User-facing Chinese labels may be naturalized, but the values MUST pass unchanged into the formal contract. Invalid values MUST fail closed and MUST NOT fall back to `other`.

The flow MUST use the formal write path:

```text
CarePathNotifier.selectReaction()
→ CarePathRepository.recordReaction()
→ PracticeRepository.recordReaction()
→ InteractionEventPayload
→ next support utterance
→ latest Garden impact
```

The UI MUST NOT synthesize a next sentence or write only onboarding-local state.

### 5.8 Next-support semantics

The next utterance is not a lesson step or random phrase. It is selected from:

```text
current care action
+ canonical child reaction
+ low-pressure communication support
```

M1 needs to show at least one next-support utterance but does not require a second completed reaction round. The exit action is a quiet “先这样就好”, not a completion or result screen.

### 5.9 First Garden trace

The first Garden trace MUST be derived from the formal Garden snapshot or impact resulting from the persisted interaction event.

The trace may show:

- care scene;
- utterance used;
- time;
- a quiet visual change.

It MUST NOT show points, coins, task completion, a streak count, child performance, or correctness.

If the reaction event is confirmed but Garden snapshot reading fails, onboarding MUST NOT roll back the real event. It may show degraded copy, mark the Garden view for refresh, and still allow entry into Today.

### 5.10 Onboarding completion contract

Onboarding may be marked complete only after:

```text
real moment started
AND parent marked the utterance as said
AND canonical reaction persisted or reconciled
AND next support resolved
AND Garden trace or valid degraded Garden state exists
```

The completed onboarding snapshot MUST persist the actual values used in the flow, including:

- age bucket;
- scene preferences;
- support goal;
- actual starter `spaceId`;
- actual starter `activityId`;
- actual starter `phraseId`;
- local-only consent state when the user skips account saving;
- completion timestamp.

It MUST NOT continue to use a separately configured fixed starter that differs from the user's real care turn.

### 5.11 Reusable authentication continuation

M1 establishes a reusable authentication continuation boundary backed by the formal account/session layer.

The continuation system should model:

- a typed pending intent;
- minimum resumable payload;
- creation and expiration;
- login return result;
- exactly-once resume attempt;
- cleanup after completion, cancellation, logout, account switch, or expiration.

The M1 intent is equivalent to:

```text
save completed onboarding memory to account
```

Successful authentication MUST persist the account session through `AccountRepository`, refresh `AccountNotifier`, resume the pending intent, then enter Today. Login failure MUST preserve the completed onboarding state and allow retry or local continuation without returning the user to the beginning.

### 5.12 Routing and legacy retirement

The public onboarding entry point becomes:

```text
/onboarding
```

Flow steps are internal state, not public routes.

The legacy paths:

```text
/onboarding/name
/onboarding/scene
/onboarding/practice
/onboarding/complete
/onboarding/garden-welcome
```

MUST no longer run the old flow. Old deep links may redirect to `/onboarding` during the cutover.

After consumers are migrated, M1 SHOULD remove or quarantine the legacy onboarding session notifier, onboarding-specific reaction and practice-record models, random phrase service, old practice/completion/Garden-welcome screens, and tests that keep the old semantics alive. No dual-write compatibility layer is allowed.

### 5.13 Resumption, failure, and unknown outcome

The design requires:

- Step selections resume after process interruption.
- An already-started care moment resumes with the same identity.
- Confirmed reaction writes are not duplicated.
- An unknown submission result enters reconciliation rather than immediately creating a new interaction event.
- A failed reaction write preserves the selected reaction and offers retry with the same logical event identity.
- A failed login does not invalidate the completed local care turn.
- A missing seed attempts a same-space safe starter, then returns to moment selection with user-safe copy if still unavailable.

### 5.14 M1 non-goals

M1 does not include:

- Custom Scene generation;
- dynamic AI content;
- a new Garden information architecture;
- background sync architecture;
- mandatory login;
- speech recognition;
- reward mechanics;
- unrelated backend changes.

### 5.15 M1 release gate

M1 is independently releasable only when it proves:

- the old onboarding flow is unreachable;
- the first care turn uses the formal Care Path;
- a canonical reaction is written as a real interaction event;
- retry/reconciliation does not duplicate the event;
- the Garden trace is not fabricated by the UI;
- the actual starter identity is saved;
- Today reads the resulting continuity;
- local-only onboarding completes without an account;
- account saving occurs only after first value;
- Custom Scene is not in the critical path;
- required unit, repository, widget, accessibility, viewport, text-scale, interruption, and error tests pass.

## 6. M2 — Custom Scene Mobile Loop

### 6.1 Outcome

When a preset scene does not match the real care moment, a parent can describe what is happening and receive an approved, playable, immediately usable care utterance that enters the same formal reaction, next-support, Garden, and Today loop as a preset scene.

```text
Today or Scene
→ describe the current moment
→ request one utterance
→ authenticate when required
→ restore input and resume once
→ wait on the same screen
→ approved generated care moment
→ playable utterance
→ “I said it”
→ canonical reaction
→ next support
→ Garden trace
→ Today continuity
```

Custom Scene is not a generic text generator or chat product.

### 6.2 Entry points

#### Today

Today provides a lightweight Custom Scene entry only when the current recommendation does not fit, the user skips it, the path is empty, or no suitable moment is available.

Example copy:

```text
不是正在发生的事？
描述一下此刻
```

The entry MUST remain visually secondary to the current playable care node.

#### Scene

Scene provides a stable secondary entry after or alongside the preset care catalog:

```text
没找到正在发生的场景？
描述一下此刻
```

Preset scenes remain the fast, reliable, and offline-capable primary option. Custom Scene does not replace the catalog.

### 6.3 Input and draft contract

The input asks for a concrete current situation, for example:

```text
宝宝坐在门口，不愿意穿鞋，一直把鞋踢开。
```

The client owns only basic input usability:

- trimming;
- empty and length checks;
- duplicate-submit prevention;
- privacy explanation;
- draft preservation.

The client does not decide content safety, age suitability, lesson framing, or generated wording. The backend Generator, deterministic gate, Judge, and bounded Repair remain authoritative.

A minimal local pending draft should include:

- source entry (`Today` or `Scene`);
- custom scene text;
- selected child identity when available;
- stable client request identity;
- resume state and expiry metadata.

The draft MUST survive the login round trip and one process interruption. It MUST be cleared after successful generation, explicit cancellation, logout, account switch, or expiration. Raw scene text MUST NOT enter analytics or ordinary logs.

### 6.4 Authentication timing and continuation

Local-mode users may open the input page and write the scene without authentication. Authentication is checked only when the user requests generation.

For an unauthenticated user:

```text
save GenerateCustomScene continuation
→ enter formal login
→ persist session through AccountRepository
→ refresh AccountNotifier
→ return to Custom Scene
→ validate continuation
→ resume exactly once
→ clear continuation after success
```

Auto-resume requires:

- a valid, unexpired continuation;
- the expected account context;
- no explicit cancellation;
- no in-flight equivalent request;
- no previously confirmed successful submission.

If auto-resume fails, preserve the draft and show a recoverable retry state. Do not send the user through login again automatically.

### 6.5 Mobile feature boundary

M2 SHOULD introduce a bounded feature such as:

```text
mobile/lib/features/custom_scene/
├── domain/
├── data/
├── application/
└── presentation/
```

The domain layer should expose a mobile-owned model such as a `GeneratedCareMoment`, not backend DTOs.

The data layer should contain strict request/response DTOs, API service, mapper, and repository implementation for the existing discovery endpoint.

The application layer owns draft state, authentication continuation, synchronous submission, idempotency/unknown outcome, error mapping, fallback, and handoff into the formal care-turn adapter.

The UI MUST NOT directly call Dio, inspect raw backend DTOs, or construct a Care Path snapshot by itself.

### 6.6 Discovery API contract

M2 consumes the existing private discovery operation:

```http
POST /api/v1/practice/discovery
```

The request uses the custom-scene mode and the normalized user scene text according to the current backend contract. Authentication and owner isolation remain mandatory.

The response mapper must retain the stable identities required for later use, including at least:

- `generatedContentId`;
- generated moment/activity identity;
- utterance identity;
- owner/account scope through authenticated access rather than exposed owner keys;
- source = Custom Scene;
- approved English, Chinese, pronunciation, action-timing, and support content needed by the care-turn path.

### 6.7 Synchronous generation state

The user remains on the input page during generation.

Recommended state progression:

```text
editing
→ needsAuthentication
→ restoring
→ submitting
→ generated
→ handoffToCareTurn
```

Recoverable failure categories include:

- input rejected;
- rate limited;
- generation rejected;
- generation unavailable;
- network unavailable;
- authentication expired;
- unknown result.

The UI MAY show a calm, non-deceptive waiting state, but MUST NOT show percentages, fake backend steps, “AI is thinking”, provider names, Judge/Repair internals, or reward animation.

Leaving the page may cancel client waiting, but the client must not assume the server operation was cancelled. Re-entry uses stable idempotency/reconciliation rather than blindly creating a second generation.

### 6.8 Idempotency and unknown result

A single user generation intent owns a stable client request identity. Network timeout or response loss MUST preserve this identity.

```text
first submit
→ fixed request identity

unknown response
→ unknown-result state
→ retry or reconcile with the same identity
→ reuse the confirmed backend result
```

The client MUST NOT create a new request identity after an unknown outcome, merge two different generated-content identities, or allow rapid taps to create parallel generation attempts.

### 6.9 Generated output handoff

The approved backend response passes through:

```text
CustomScene DTO
→ CustomScene mapper
→ GeneratedCareMoment
→ generated-care-turn adapter
→ CarePath presentation contract
→ standard one-turn UI
```

Custom Scene MUST NOT have a standalone “AI result” experience.

The resulting one-turn surface uses the same product semantics as preset content:

- English parent utterance;
- Chinese meaning support;
- action timing;
- pronunciation;
- audio;
- “I said it”;
- canonical reaction;
- next support;
- Garden trace;
- quiet exit.

Generated content MUST remain identifiable and persistable. It cannot be reduced to UI-only strings, a fake activity, or a parallel reaction session.

### 6.10 One bounded generated care moment

One generation should return or resolve enough approved content to execute a bounded care moment, including the starter and the reaction-aware support required by the formal path.

M2 MUST NOT call open-ended generation again for every child reaction. Reaction handling must use approved branches/support utterances or the formal deterministic runtime/repository contract.

### 6.11 Real-time generated speech

M2 uses backend real-time TTS with no persistent audio storage.

The recommended endpoint semantics are:

```http
GET /api/v1/practice/generated-content/{generatedContentId}/utterances/{utteranceId}/audio
```

Equivalent POST semantics are acceptable if required by the final implementation contract, but the following requirements are fixed:

- the client submits stable generated-content and utterance identity, not arbitrary text;
- the server authenticates the account;
- the server verifies owner access;
- the server verifies the generated content and utterance are approved and playable;
- the server reads the approved English text;
- the server synthesizes speech through a typed provider port;
- the server streams or returns bounded audio bytes;
- the server does not write an audio database record;
- the server does not create a file;
- the server does not use object storage;
- request memory is released after the response;
- TTS failure does not change generated-content approval state or rerun content generation.

The TTS provider boundary should be typed and configuration-driven. Controllers must not select providers directly.

### 6.12 Mobile session-only audio cache

The generated audio decision is fixed:

> The backend synthesizes audio in real time without persistence. The mobile client keeps only a bounded session-level in-memory cache. Audio does not go to disk, Isar, SharedPreferences, backup, or cross-process storage.

Recommended architecture:

```text
GeneratedAudioRepository
├── GeneratedAudioApi
├── GeneratedAudioMemoryCache
└── CareAudioPlaybackController
```

The cache key includes only stable non-sensitive identity and audio contract dimensions:

```text
generatedContentId
+ utteranceId
+ voiceVersion
+ format
```

It MUST NOT contain raw scene text, English text, child names, phone numbers, or owner HMAC values.

The cache MUST implement:

- bounded LRU eviction;
- a total-byte limit as well as an item limit;
- TTL;
- single-flight request coalescing for the same key;
- account/lifecycle clearing;
- rejection of empty, oversized, or invalid MIME responses;
- protection against late responses playing after the user leaves or the active utterance changes.

Initial implementation parameters may target approximately 12 items and 45 minutes, but exact values may be adjusted through device and response-size tests. The bounded and non-persistent requirements are non-negotiable.

The cache clears on logout, account switch, consent withdrawal, account deletion, incompatible voice-contract change, or process termination.

The current asset-only audio control should evolve into a source-neutral abstraction supporting packaged assets and generated bytes while preserving the existing seed-audio behavior.

A temporary-file cache is not part of M2. It may be considered only through a later explicit design if Android byte-source playback proves unreliable on supported devices.

### 6.13 Failure and fallback

- Input rejection preserves the editable draft and uses non-accusatory copy.
- Generation failure offers retry and a route back to preset scenes.
- Rate limiting explains that generated help is temporarily unavailable while preset scenes remain usable.
- Network failure preserves the draft.
- TTS failure keeps the approved text usable and does not block “I said it”, reaction, or Garden.
- Reaction-write failure follows the same stable event identity and reconciliation contract as M1 and the formal one-turn path.
- Preset scenes remain usable when AI or TTS is unavailable.

M2 does not require semantic fallback search. A stable return to selected or nearby preset-scene scope is sufficient.

### 6.14 Today continuity

After a Custom Scene reaction is confirmed, Today must reflect the recent generated care moment, current/next utterance, last reaction, and Garden continuity as supported by the formal repositories.

M2 does not require a permanent custom-scene history or insertion into the public preset catalog.

### 6.15 Privacy requirements

Custom Scene is private family content.

M2 MUST enforce:

- generation requires an authenticated account;
- pre-login draft remains local until submission;
- generated content is owner-scoped;
- mobile models and logs never expose owner HMAC values;
- the TTS endpoint is owner-checked and cannot synthesize arbitrary client text;
- generated audio is not persisted by backend or mobile;
- in-memory audio is never shared across accounts;
- logout/account switch clears draft, continuation, and audio cache;
- private generated content never becomes public catalog content through the mobile fallback.

### 6.16 M2 non-goals

M2 does not include:

- background generation;
- push notifications;
- polling as a normal product path;
- custom-scene history management;
- editing approved generated content;
- sharing generated content;
- multi-turn chat;
- open-ended regeneration after every reaction;
- semantic-reuse UI;
- a global visual redesign;
- reward mechanics.

### 6.17 M2 release gate

M2 is independently releasable only when it proves:

- M1 onboarding and preset scenes do not regress;
- Today and Scene entry points are both usable and correctly prioritized;
- unauthenticated input is preserved;
- login resumes generation exactly once;
- request identity survives timeout and unknown outcome;
- strict DTO mapping preserves generated identity and approved content;
- generated content enters the formal care-turn path;
- canonical reaction creates a real event and Garden trace;
- Today reflects the generated continuity;
- TTS verifies owner and approved utterance identity;
- backend audio is not persisted;
- mobile audio is memory-only, bounded, TTL-controlled, and single-flight;
- TTS failure does not block the care turn;
- AI/TTS failure does not block preset scenes;
- required backend, mobile unit, repository, widget, privacy, audio, accessibility, and real-device tests pass.

## 7. M3 — Care Path Visual Cohesion

### 7.1 Outcome

M3 makes the stable primary surfaces feel like one product:

```text
new onboarding
→ Today
→ Scene
→ one-turn
→ Garden
→ My
```

It does not add new core capability or redesign the four-tab IA. It creates a quiet, warm, immediately understandable product rather than a course, child classroom, or task dashboard.

### 7.2 Visual principles

#### The speakable utterance remains the hero

In care-turn surfaces, visual priority is:

```text
English utterance
→ Chinese meaning support
→ action timing
→ audio
→ “I said it”
→ reaction/context adjustment
```

Illustration, Garden, character, and decoration remain secondary.

#### One dominant action per screen

Each screen should have one visually dominant primary action. Secondary actions must remain quieter.

#### Reduce indiscriminate card usage

Main content should use open layout or a sentence light field. Collections may use light surfaces. Status feedback should remain inline. Cards are reserved for content that truly needs grouping. Avoid dashboard-like equal-weight modules, nested cards, and strong shadows.

#### State changes happen in place

Utterance, reaction, next-support, saving, error, and reconciliation states should update in place rather than forcing unnecessary navigation or modal sheets.

#### Garden is memory, not reward

Garden visuals express that a real family-English moment happened. They do not celebrate task completion or performance.

### 7.3 Visual token scope

M3 should consolidate only the repeated semantic tokens required by the primary paths:

- colors;
- typography;
- spacing;
- radii;
- elevation;
- motion;
- touch targets.

The approved visual direction retains warm paper, near-white sentence light field, deep warm text, quiet green action color, and low-saturation warm accent. Existing values such as the following may remain the baseline pending implementation validation:

```text
warm paper       #FBF6EF
sentence field   #FFFDF9
primary text     #302A26
secondary text   #6D625B
weak text        #887C74
quiet green      #3F746B
soft green fill  #E4F0EC
warm accent      #B9653B
```

M3 does not build a speculative general-purpose design system.

### 7.4 Shared visual components

M3 MAY extract focused semantic components such as:

- `CarePageScaffold`
- `PrimaryCareAction`
- `CareUtteranceSurface`
- `CareAudioControl`
- `BabyReactionSelector`
- `InlineCareStatus`
- `GardenTracePreview`

Components own presentation, accessibility, and state rendering. They MUST NOT read repositories or contain business transitions.

The audio control presents the same visual states for seed assets and generated bytes:

```text
idle / loading / playing / paused / failed
```

### 7.5 Onboarding visual treatment

Onboarding uses a stable shell:

```text
light progress cue
→ one question or current utterance
→ selection/feedback region
→ bottom primary action
```

Progress may provide orientation but MUST NOT use course-style numeric completion, percentages, steps, or reward animation.

Selection does not auto-advance. The user selects, then confirms through the primary CTA.

The onboarding care-turn surface should visually converge with the formal one-turn surface so entry into Today does not feel like a product switch.

### 7.6 Today visual treatment

Today highlights one dominant current care node. It is not a dashboard.

Priority is:

```text
current care node
→ short immediate-value cue
→ enter
→ light recent continuity
→ secondary alternatives
```

Custom Scene appears only as a lower-priority contextual escape when the recommendation does not fit, the path is empty, or the user explicitly rejects the current node.

Recent continuity may show a recent scene, utterance, or Garden change, but not learning statistics or an activity feed.

### 7.7 Scene visual treatment

Scene remains discovery and selection rather than a learning map.

Suggested structure:

```text
page title
→ common preset care scenes
→ recent use
→ Custom Scene secondary entry
```

Preset scene items may show scene name, typical care action, and quiet illustration. They MUST NOT show lessons, completion counts, difficulty ranks, stars, locked nodes, or score.

Offline state still prioritizes usable preset scenes.

### 7.8 One-turn visual treatment

The one-turn surface is M3's most important screen.

Stable hierarchy:

```text
scene/action context
→ English utterance
→ Chinese support
→ action timing
→ “听一下”
→ “我说了”
→ reaction selector
→ next support
→ Garden trace
→ “先这样就好”
```

The approved sentence light-field direction remains:

- no hard card border;
- quiet central region;
- illustration at the edges;
- main utterance remains visually stable.

The audio control uses icon plus text and does not show a progress bar.

After “我说了”, the canonical reaction selector expands in place. The old utterance may fade out and the new support utterance fade in. With reduced motion enabled, state changes occur directly without relying on animation.

“先这样就好” exits quietly. There is no result page, score, summary, or completion celebration.

### 7.9 Garden visual treatment

Garden emphasizes recent real care traces and quiet continuity.

A trace may include:

- time;
- care scene;
- utterance used;
- natural-language reaction context;
- next support.

Reaction display is factual context, not performance evaluation.

Garden growth may use a new leaf, subtle light, plant posture, or another gentle visual memory. It MUST NOT use reward popups, rarity, collection pressure, currency, or streak-loss mechanics.

### 7.10 My visual treatment

M3 does not redesign My's IA. It aligns presentation for:

- child and family;
- account and sync;
- audio/language preferences;
- privacy and data;
- help/about.

Local-mode users should clearly understand that current data remains on this device and can be saved to an account without alarmist or coercive copy.

### 7.11 Unified state language

M3 establishes distinct but consistent visual states for:

- initial page loading;
- action submission;
- audio preparation;
- Custom Scene generation;
- reconciliation/unknown result;
- inline error;
- empty state.

Do not use one generic full-screen spinner for all conditions.

Errors should appear in context with one clear recovery action, such as retry, choose another scene, continue reading, or return to preset scenes.

Unknown outcome remains distinct from failure and prioritizes reconciliation.

### 7.12 Motion

Motion serves continuity and state feedback only. Approved patterns include short fades, gentle reaction expansion, subtle Garden trace appearance, and primary-button press feedback.

M3 prohibits bouncing reward motion, flashing, confetti, coin movement, streak flames, reward boxes, or unskippable celebration.

Reduced-motion mode removes translation and non-essential fades while preserving state clarity.

### 7.13 Illustration and companion character

M3 may use existing family line art or the approved TaTa companion direction sparingly. It does not implement a full ritual-illustration system.

Allowed use includes a quiet Today illustration, light Scene line art, edge illustration around the sentence field, subtle Garden growth, and low-frequency companion guidance.

The character is a companion, not a task manager, teacher, scorer, or reward distributor.

### 7.14 Accessibility and semantic order

The one-turn semantic order remains stable:

1. English utterance;
2. Chinese meaning;
3. action timing;
4. audio action;
5. context/reaction action;
6. quiet exit.

Decorative illustration is excluded from the semantic tree. The utterance is read as a complete sentence. Loading and result changes use restrained live-region announcements. Unknown-outcome focus prioritizes recovery. New support focus moves deliberately and must not repeatedly steal focus.

Today, Scene, Garden, Onboarding, and My also require stable linear semantics.

### 7.15 Responsive layout and text scaling

Required acceptance viewports:

- 390 × 844 dp;
- 427 × 952 dp;
- 1.0× text;
- 1.3× text.

The implementation should additionally spot-check 320 dp width and 2.0× system text to avoid catastrophic failure.

Critical layout rules:

- English utterances may wrap;
- bottom CTA never hides content;
- small screens scroll rather than shrink touch targets;
- reaction options wrap or become vertical;
- critical text is not ellipsized;
- keyboard does not make input or CTA unreachable;
- touch targets remain at least 48 dp.

### 7.16 Screenshot, golden, and semantics strategy

Use page-level screenshot coverage for the highest-value states, including:

- onboarding choice and first care-turn;
- Today normal and Custom Scene escape;
- Scene catalog;
- Custom Scene input/loading/error;
- seed and generated one-turn;
- reaction expanded;
- next support;
- Garden trace.

Use component-level golden tests only for stable semantic components such as the utterance surface, audio control, reaction selector, primary action, Garden trace preview, and inline status.

Golden tests do not replace semantic order, text scale, touch target, motion, focus, or error-state tests.

## 8. Cross-milestone data and state rules

### 8.1 Formal identity

Every persisted care interaction must retain enough identity to distinguish:

- preset content;
- private generated content;
- utterance identity;
- care moment/activity;
- interaction event;
- account/local owner context as appropriate.

UI strings are never the system of record.

### 8.2 Exactly-once user intent

Onboarding reaction submission, Custom Scene generation, authentication continuation, and Garden trace creation require stable logical identities and idempotent resume behavior. Unknown outcome is a first-class state, not a generic error.

### 8.3 Privacy lifecycle

Logout, account switch, consent withdrawal, and account deletion must clear all account-scoped pending continuations, private drafts, and in-memory generated audio. Persistent local-sensitive-data clearing continues to use the existing registered clearance architecture where persistence exists.

### 8.4 Fail-open and fail-closed boundaries

Fail closed for:

- invalid canonical reaction;
- unauthorized generated content;
- arbitrary-text TTS;
- owner mismatch;
- invalid/oversized audio;
- ambiguous successful submission identity.

Fail open for continued user value where safe:

- audio unavailable while approved text remains readable;
- Garden snapshot temporarily unavailable after event confirmation;
- AI/TTS unavailable while preset scenes remain usable;
- account saving skipped after local first value.

## 9. Testing strategy across the roadmap

Every milestone includes:

- unit tests for state machines and policy;
- repository/service tests for formal data paths;
- widget tests for user flows and state rendering;
- accessibility tests;
- copy-firewall verification;
- viewport and text-scale checks;
- interruption, retry, duplicate-tap, and unknown-outcome tests;
- local full-CI execution before release.

M2 additionally requires backend contract, owner/privacy, TTS non-persistence, output-size, MIME, timeout, and provider-failure tests.

M3 additionally requires screenshot/golden and real-device UAT evidence.

Passing tests from a prior milestone cannot replace fresh verification at the release candidate commit.

## 10. Delivery sequence

The implementation sequence is fixed:

1. Write and approve an implementation plan for M1.
2. Implement, verify, review, and independently release M1.
3. Write and approve an implementation plan for M2 against the post-M1 baseline.
4. Implement, verify, review, and independently release M2.
5. Write and approve an implementation plan for M3 against the post-M2 baseline.
6. Implement, verify, review, and independently release M3.

Do not create one giant implementation plan spanning all three milestones. Each milestone has its own spec-to-plan-to-implementation cycle and release gate.

## 11. Final approved decisions

The following decisions are locked by this design:

- Use roadmap A+: onboarding value first, Custom Scene second, visual cohesion third.
- Each milestone is independently runnable, testable, acceptable, and releasable.
- First value precedes account saving in onboarding.
- Custom Scene appears in both Today and Scene with different visual priority.
- Custom Scene generation waits synchronously on the current page.
- An unauthenticated user may write a Custom Scene draft; authentication is required only on submission, and the draft resumes after login.
- M3 unifies visual language without changing the four-tab IA.
- Generated speech is synthesized by the backend in real time.
- The backend does not persist generated audio.
- The mobile client uses bounded session-only in-memory audio caching with LRU, TTL, total-byte limits, and single-flight.
- Generated audio never goes to disk in M2.
- Reward economy is outside all three milestones and is not prebuilt.
