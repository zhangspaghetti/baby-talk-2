### Step 1/4: arch_review（软件架构师）

1. App 组合根过载。严重程度：高。修复成本：中。影响：启动、依赖装配、会话恢复、路由与重入编排都堆在 app 层，新增一个 feature 往往要回到根部改 wiring，变更难以局部化，后续团队并行会越来越痛。证据：mobile/lib/app/app.dart、mobile/lib/app/providers/repository_providers.dart。建议修复：把 app 层收敛成纯 composition root，只保留 boot、router、root widget；每个 feature 暴露自己的 provider/facade；把启动期编排拆到独立的 application/boot 模块，而不是继续往 app.dart 里堆。

2. 限界上下文被横向依赖打穿。严重程度：高。修复成本：中。影响：practice、onboarding、mentor、household、share 看起来是按 feature 切目录，但实际通过直接引用彼此内部类型来协作，一个上下文改模型会联动多个模块，扩展新业务时会越来越像大泥球。证据：mobile/lib/features/mentor/data/repositories/mentor_repository.dart 同时依赖 household、onboarding、practice，甚至依赖了 practice 的 presentation 类型；mobile/lib/features/onboarding/data/repositories/onboarding_repository.dart 直接依赖 PracticeRepository；mobile/lib/features/share/domain/models/share_link_draft.dart 直接耦合 practice 域模型；mobile/lib/features/practice/presentation/screens/home_screen.dart 直接拼装 account、household、mentor、share 的 UI。建议修复：先定义每个 bounded context 的公开 contract，只允许跨 feature 通过 facade、DTO 或 application service 交互；像 home/garden 这种跨域编排页面应上移到 shell/application 层，而不是留在 practice feature 内部。

3. 分层不完整，UI 与导航契约直接依赖 data 层细节。严重程度：高。修复成本：中。影响：当前不是稳定的 UI → application → domain → infrastructure 依赖方向，而是 presentation 经常直接拿 repository、本地存储甚至路由模型，导致测试替身、离线替换、后续抽包都很难做。证据：mobile/lib/features/practice/presentation/practice_session_view_model.dart 直接依赖 PracticeRepository；mobile/lib/features/household/presentation/widgets/household_shared_context_card.dart 直接依赖 local store 与 practice route args；mobile/lib/features/shell/presentation/widgets/garden_hero_card.dart 和 mobile/lib/features/shell/presentation/widgets/garden_continue_card.dart 直接拿 repository 暴露的快照类型；mobile/lib/features/practice/presentation/practice_route_args.dart 把 go_router 与 seed content 校验揉在一个 presentation 类型里。建议修复：补一个轻量 application 层，统一输出 view state 和 command；route args 移到 app/router contract；widget 只消费 view state，不直接碰 repository/local store。

4. 状态管理与路由迁移长期停留在双轨制。严重程度：中。修复成本：中。影响：团队需要同时理解 Provider、Riverpod、Hooks、ChangeNotifier、ViewModel/Notifier 两套表达，以及旧 Navigator 路由和 go_router 两套导航语义，认知负担和生命周期 bug 风险都在上升。证据：mobile/pubspec.yaml 同时声明 provider、flutter_riverpod、hooks_riverpod、flutter_hooks；同一 feature 中普遍存在成对文件，如 mobile/lib/features/account/presentation/account_view_model.dart 与 mobile/lib/features/account/presentation/account_notifier.dart，mobile/lib/features/mentor/presentation/mentor_view_model.dart 与 mobile/lib/features/mentor/presentation/mentor_notifier.dart；mobile/lib/app/router/app_router.dart 已标记废弃，但 mobile/lib/app/router/app_go_router.dart 又已并存。建议修复：立一个 ADR，明确新代码只允许一种状态模型和一种路由模型；按 feature 分批迁移，完成一个删一个，不再长期保留镜像 API。

5. 技术选型没有完全收敛，依赖图已经出现兼容性补丁信号。严重程度：中。修复成本：低到中。影响：这不是立刻会炸的债，但会持续抬高升级成本和排障成本，尤其是 Flutter 生态升级频繁时。证据：mobile/pubspec.yaml 同时保留多套重叠能力依赖，并在 mobile/pubspec.yaml#L49 使用 dependency_overrides 固定 win32 版本；代码里又能看到 Riverpod、Provider、Hooks、go_router 混用，例如 mobile/lib/app/app.dart、mobile/lib/features/practice/presentation/screens/home_screen.dart、mobile/lib/features/account/presentation/screens/account_entry_screen.dart。建议修复：做一次依赖收敛 ADR，明确网络层、状态层、路由层各自唯一主栈；把 override 当成临时债登记并设置移除时间点；如果 legacy 兼容必须保留，也要把它们限制在 adapter 层，而不是继续向业务代码扩散。

总体判断：这个 mobile 代码库本质上是一个 feature-first 的模块化单体雏形，方向并不差，尤其是账户、练习、家庭、导师、分享这些业务主题已经能看出 bounded context 意识；但目前更像“共享进程里的多 feature 互相借内部类型”，还不是依赖方向被真正锁住的模块化单体。抽样中我没有看到必须推倒重来的信号，也没发现明确的编译级循环依赖证据；更现实的路线是先在单体内收紧边界，而不是急着做更重的拆分。

如果要给出两条演进路径，我会推荐方案 A：继续保持单体，但给每个 feature 建立公开 contract、完成状态/路由收敛、把 application 层补齐。这条路成本更低、可逆性更强，也最符合当前仓库形态。方案 B 是把稳定 contract 进一步抽成内部 Dart package，边界更硬，但构建、发布和迁移成本会明显更高，现阶段不必先走到这一步。
