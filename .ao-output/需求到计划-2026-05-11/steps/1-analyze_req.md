### Step 1/3: analyze_req（产品经理）

# 需求分析

## 1. 需求理解
本次需求不是新增功能，而是把两份评审报告转成一套可执行的整治计划，让 Baby Talk 2 Phase 1 从“方向正确但内部复杂、体验分散”的状态，进入“核心路径稳定、界面聚焦、无障碍达标、可持续交付”的状态。范围同时覆盖技术债治理和 UX 改造，目标是先解决发布阻塞项，再建立持续演进的工程与体验基础。

## 2. 用户价值分析
- 对家长用户：降低首次开口和持续练习的认知负担，让首页和练习页更直接、更可靠、更易访问。
- 对使用辅助技术的用户：补齐动态播报、焦点管理、减少动效和关键组件语义，避免关键流程无法完成。
- 对研发团队：减少双真相源、路由/状态混乱和回归不确定性，缩短定位问题和交付需求的时间。
- 影响范围：几乎覆盖 Home、Practice、Garden、Mentor、Account/Sync、启动恢复、分享/邀请回流、CI/QA 全链路。

## 3. 功能范围界定
### MVP 包含
1. 统一核心链路的状态 Owner，明确单一状态主栈。
2. 建立默认 PR 稳定性门禁、覆盖率基线和快速 integration pack。
3. 把 app 层收口为 composition root，抽离 boot/reentry/session 协调逻辑。
4. 首页与练习页聚焦单一主任务，移除工程态/说明态噪音。
5. 重构 4-tab、Drawer、Mentor FAB 的职责边界。
6. 建立动态状态播报、焦点管理、减少动效与关键组件语义。
7. 账号/同步入口分层、统一术语与本地化语义。
8. 建立错误分类、结构化日志和发布前手动无障碍回归清单。

### MVP 不包含
1. 新的 Mentor 智能策略或更深的情境推荐能力。
2. Growth/Garden 的长期动力系统增强。
3. 大规模视觉品牌重设计。
4. 全量 feature 模块化拆包或平台级重写。
5. 非当前主路径的低频优化和装饰性 polish。

## 4. 优先级排序
### P0
- 核心状态统一与回流链路迁移：直接决定主路径稳定性和后续重构能否继续。
- 默认 PR 门禁与覆盖率基线：没有门禁就无法安全推进重构。
- 首页与练习页主任务聚焦：直接影响“现在就说一句”的核心价值是否被感知。
- 动态无障碍与焦点管理：属于发布阻塞项，当前无法判定 WCAG 2.1 AA 合规。

### P1
- app 层收口与 application/view state 层补齐：降低根部热点和 UI 直连 data/router 的问题。
- 全局导航/账号同步信息架构重构：减少重复入口和风险操作暴露。
- bounded context contract 与统一错误语义：为后续演进建立可维护边界。

### P2
- 热点文件拆分、技术栈 ADR、长期 Growth/Mentor 优化：重要但不应阻塞首轮整治闭环。

## 5. 验收标准
1. Home 首屏只保留一个清晰主 CTA，并能承接继续/开始今日练习。
2. Practice 首屏只保留关键任务信息，不再暴露工程态、重复入口或过多说明。
3. 启动恢复、深链接、分享、邀请接受等关键回流不再直接修改 legacy ViewModel/Provider。
4. PR 默认门禁可执行 analyze、targeted unit/widget、quick integration pack 与 coverage threshold。
5. Drawer、Bottom Sheet、Mentor 面板等关键弹层具备初始焦点、焦点返回与屏幕阅读器可感知状态。
6. 离线、重连、录音、播放、失败、完成、限流等动态状态能被统一播报。
7. 账号、同步、共享、高风险设置完成分层，用户能区分高低频与高风险操作。
8. 发布前完成 TalkBack、VoiceOver、键盘、大字号、深浅色、减少动效的回归结果留档。

## 6. 风险点和待确认事项
1. 单一状态主栈是否明确以 Riverpod/Notifier 为目标，如未确认会影响后续迁移决策。
2. 现有测试基础是否足够支撑覆盖率阈值，如果基线过低需分阶段抬升。
3. UX 改造是否允许在一个版本内对导航与首页信息架构做明显调整。
4. 无障碍手动验证设备与系统版本矩阵需要提前锁定，否则发布前补测可能排期失控。
5. 文案与术语统一需要产品/设计指定 owner，否则容易在开发中反复回滚。
6. 迁移过程中需要 feature freeze 或变更窗口，否则双栈并存时间会被继续拉长。
