### Step 3/4: security_review（安全工程师）

# 安全评审

## 评审意见

1. 🔴 高：认证不等于授权，外部 API 存在对象级越权风险。当前只写“高风险动作校验登录态”，未定义 account/share/session 资源的服务端 owner check、scope check 和默认拒绝策略。
修复方案：补主体-资源-动作-条件的授权矩阵；所有接口从服务端会话解析主体，不信任客户端 owner；高风险 consent 变更追加 re-auth 或 step-up auth，并写入不可抵赖审计记录。

2. 🔴 高：恢复 token / 邀请 token 只要求“不写日志”远远不够，缺少 TTL、一次性消费、吊销和重放防护设计。
修复方案：对恢复/邀请 token 使用短时效、一次性、服务端哈希存储、消费后立即失效，并绑定用途、用户和设备上下文；access/refresh token 分开治理并支持 revoke。

3. 🔴 高：BootCoordinator 的本地恢复信任边界不清，存在伪造或陈旧认证状态风险。
修复方案：把本地 auth state 明确定义为非权威缓存；进入敏感流程前必须经服务端确认 session；本地仅存最小必要凭据并放 OS 安全存储。

4. 🔴 高：数据安全要求不完整，尤其是 Local Store、Audio/TTS/ASR、日志与第三方 AI/语音服务的数据出境控制不足。
修复方案：先做数据分类；账号标识、语音、转写文本、练习结果按敏感数据处理；传输强制 TLS；敏感字段默认不明文落盘；日志、埋点、错误上报统一脱敏；第三方 TTS/ASR 单独做数据处理评审。

5. 🟡 中：输入验证方案缺失，类型安全不能替代服务端校验。
修复方案：为每个外部接口做 schema 校验、字段 allowlist、长度/字符集限制、枚举校验和体积限制；所有展示到 Web/Admin 的文本做上下文相关转义；日志字段做控制字符清洗。

6. 🔴 高：API 防滥用设计缺位，缺少限流、防刷、重放防护和 CSRF/CORS 策略。
修复方案：按接口价值配置 IP、账号、设备、token 分层限流；写接口要求幂等键或 nonce；需要 cookie 的 Web 入口启用 CSRF token + SameSite；CORS 政策显式 allowlist。

7. 🟡 中：Consent 与共享链路缺少不可抵赖设计，既有安全风险也有合规风险。
修复方案：将 consent 设计为事件流而不是单个布尔值，记录 `policyVersion`、`policyHash`、`actor`、`authStrength`、`timestamp`、`device/appVersion`；支持撤回但不覆盖历史。

8. 🟡 中：依赖与供应链控制不足，CI 门禁目前偏质量而非安全。
修复方案：把 SCA、SBOM、secret scanning、lockfile 校验、依赖来源限制和制品签名纳入门禁；Flutter、npm、Maven 多生态统一做准入和更新策略。

9. 🟡 中：审计日志有方向但缺规范，容易出现既审不到关键事件，又泄露过多敏感上下文的问题。
修复方案：单独设计 security audit schema，覆盖登录、token 消费、consent 变更、权限拒绝、异常访问模式；敏感字段哈希化或截断，并配置保留周期和访问权限。

10. 🔴 高：若产品处理儿童语音、成长记录或家庭账号信息，当前隐私合规条款明显不足。
修复方案：将儿童/家庭数据列为高敏数据；补家长同意、最小必要采集、删除权、导出权、第三方处理清单、留存与删除矩阵；任何新用途必须重新评估合法性基础。

## 总体结论
方案有正确的安全方向，但当前仍停留在原则层，缺少可执行的安全契约。最主要风险集中在对象级授权、token 重放、启动恢复信任边界、敏感数据保护和审计/隐私治理。

## 评审结论
在补齐授权矩阵、token 生命周期、启动恢复校验、数据分类与 API 防滥用机制之前，不建议将此文档直接作为上线前安全基线。
