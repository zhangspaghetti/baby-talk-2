### Step 2/4: arch_review（后端架构师）

# 后端架构评审

## 评审意见

1. ✅ 合理：整体采用“模块化单体 + application/coordinator + shared contracts + facade”的方向正确，符合当前“增量重构而非重写”的约束，能先解决状态双写和 app 层失控问题。
建议：尽快把 application 层定义为“编排层而非业务实现层”，禁止直接依赖 UI 组件、第三方 SDK 细节和 feature 内部状态对象。

2. ⚠️ 建议优化：当前分层图清晰，但职责边界还不够可执行，BootCoordinator、HomeOrchestrator、PracticeCoordinator、SyncSettingsCoordinator 都带有“总控”色彩，后续容易出现 application 层横向耦合。
建议：为每个 coordinator 补输入边界、输出边界和依赖边界三类规则，只接收 contract DTO/command，只返回 view state 或 intent，只依赖 contract、facade、repository interface。

3. ❌ 需要重新设计：内部 contract API 只给了接口名，没有定义同步/异步语义、幂等性、失败语义和状态机约束，无法支撑关键启动链路和练习链路的稳定重构。
建议：补齐 `resolveStartup`、`buildPrimaryTask`、`practice.dispatch` 的超时、重试、错误分类、非法状态处理、幂等和去重规则。

4. ⚠️ 建议优化：性能目标只写了 P95，没有说明延迟预算分布在哪一层，也没有说明缓存、预加载、异步流水线或去抖策略。
建议：按启动恢复、首页主 CTA、practice command 三条链路拆解预算，并明确哪些步骤走本地快照、哪些步骤异步校正。

5. ⚠️ 建议优化：当前方案没有明确缓存策略。`/api/account/sync-status`、`/api/account/share-consent`、`/api/practice/session-results` 在流量增长后会成为热点。
建议：为 sync-status 定义 ETag/版本缓存，为 share-consent 定义幂等更新，为 session-results 定义本地队列补偿或异步写入。

6. ✅ 合理：保留模块化单体、暂不拆包/拆服务是正确判断。现阶段核心问题是边界污染和状态真相源失控，而不是部署拓扑不够复杂。
建议：即使不拆服务，也要按未来可拆的方式稳定 practice、share、growth 的输入输出模型。

7. ❌ 需要重新设计：可扩展性部分没有覆盖“10 倍流量”下的后端承载策略，缺少热点接口、写放大、日志放大、音频上传峰值、异步任务积压的容量视图。
建议：补一张后端容量图，明确读路径、写路径、重任务和日志链路的峰值行为及削峰策略。

8. ⚠️ 建议优化：容错与高可用设计偏弱。虽然定义了 ErrorEnvelope 和结构化日志，但缺少降级、超时、重试、单点识别与补偿设计。
建议：为启动恢复、练习链路、账号同步分别定义失败路径、超时上限、指数退避和后台补偿策略。

9. ❌ 需要重新设计：数据一致性策略缺失。启动恢复、分享回流、邀请接受、账号同步、练习结果回传之间，谁是 source of truth、冲突如何合并、失败如何补偿，都没有说明。
建议：明确本地与服务端真相源边界、冲突解决原则、写入补偿机制和顺序保障粒度。

10. ⚠️ 建议优化：数据模型过于抽象，只列模型名称，没有体现关键查询模式与索引匹配关系。
建议：至少补充启动恢复、首页主任务、练习结果三类关键访问模式，并映射到索引与 DTO。

11. ⚠️ 建议优化：角色要求中提到实时链路与有序性，但正文没有体现任何 WebSocket/实时推送设计。
建议：明确 Phase 1 是否完全不引入实时链路；如果需要，就补连接生命周期、顺序键、去重键和重连策略。

12. ✅ 合理：`shared/contracts` 中定义 TypedRouteArgs、ViewState DTOs、ErrorEnvelope 是对抗跨模块隐式耦合的有效手段。
建议：继续将共享 DTO 控制在稳定、少量、语义明确的范围内，避免 shared/contracts 演变成新泥球。

13. ⚠️ 建议优化：`ErrorEnvelope` 只是错误包装还不够，需要错误分级与处置矩阵。
建议：把错误分成用户可恢复、用户不可恢复、系统可重试、仅开发者可观测四层，并绑定 UI 与日志策略。

14. ❌ 需要重新设计：质量门禁只定义了 analyze、tests、quick pack、coverage 阈值，但没有把门禁和 contract 变更、关键行为边界绑定。
建议：补充 contract 兼容性检查、启动恢复/dispatch/sync 行为测试、协议 schema snapshot 和外部 API 错误码回归。

15. ⚠️ 建议优化：迁移期间缺少控制红线。文档说要消灭双写，但没有定义过渡期白名单、legacy 写入口监测和可删除资产清单。
建议：建立迁移白名单，对 legacy 写入加监测日志/断言，并在每个里程碑绑定可删除资产。

16. ⚠️ 建议优化：可观测性目前只有结构化日志，不足以支撑重构后的稳定性证明。
建议：补充关键指标、correlation id 和告警设计，包括启动恢复耗时、practice command 成功率、sync 失败率和补偿队列积压量。

17. ✅ 合理：里程碑按“先边界与护栏，再迁移状态，再重构体验，最后清理闭环”的顺序是对的。
建议：为每个里程碑增加退出条件，例如 M3 的退出条件应是“关键主路径 legacy 写入归零”。

## 总体结论
方向正确，适合作为 Phase 1 主方案；但当前文档更像“重构意图说明”，还不是可直接实施的技术设计。需要先补齐关键接口契约执行语义、数据一致性与补偿、容量视图、查询模式与索引设计，再进入开发。

## 评审结论
有条件通过。
