### Step 4/4: review_summary（代码审查员）

# 技术方案评审结论

## 总体评价
有条件通过。

这份方案的战略方向是正确的：它准确抓住了当前 Baby Talk 2 Phase 1 的核心问题不是缺功能，而是状态双写、边界失效、主路径分散和发布护栏不足；在此基础上提出“模块化单体 + 单一状态主栈 + application/contract 收口 + 无障碍服务层 + 分层门禁”的主线，也符合当前代码库和团队节奏。

但当前文档仍偏“重构意图说明”，还不是可以直接实施的完整技术设计。阻塞项主要集中在三类：
1. 关键接口与状态机契约还没有可执行定义。
2. 安全与一致性边界没有下沉到规则级设计。
3. 容量、补偿、查询模式和审计门禁还没有落实到验证标准。

## 必须修改（阻塞项）

1. 启动恢复、首页主任务、Practice dispatch 三条核心内部 contract API 必须补齐执行语义。
修改要求：明确同步/异步语义、超时阈值、幂等与去重规则、非法状态处理、ErrorEnvelope 映射和状态机边界。
来源：架构评审 `❌`。

2. 必须补充本地状态与服务端状态的一致性模型。
修改要求：定义 source of truth、冲突合并、失败补偿、重复提交防护和事件顺序保障粒度，覆盖启动恢复、分享回流、邀请接受、账号同步、练习结果回传。
来源：架构评审 `❌`。

3. 必须补一张面向 10 倍流量的容量与热点链路设计图。
修改要求：明确启动/首页读路径、练习结果写路径、音频/ASR/TTS 重任务、日志链路和削峰/异步化策略。
来源：架构评审 `❌`。

4. 必须把关键查询模式映射到数据模型、索引与缓存策略。
修改要求：至少覆盖启动恢复、首页主任务、练习结果 3 类关键访问模式，并给出索引与缓存/版本策略。
来源：架构评审 `❌`。

5. 所有外部 API 必须补服务端授权矩阵，不能只校验登录态。
修改要求：为 `/api/account/sync-status`、`/api/account/share-consent`、`/api/practice/session-results` 定义 owner check、scope check、tenant check、默认拒绝与高风险动作 step-up auth。
来源：安全评审 `🔴`。

6. 恢复 token、邀请 token、access token、refresh token 必须补完整生命周期设计。
修改要求：TTL、一次性消费、哈希存储、吊销、旋转、重放防护、设备/用途绑定、失败后的默认拒绝。
来源：安全评审 `🔴`。

7. BootCoordinator 的认证恢复必须改成“本地缓存提示 + 服务端权威确认”模型。
修改要求：敏感流程不得只依据本地状态恢复；本地凭据仅存 OS 安全存储；auth state 拆为 anonymous、pending-reauth、authenticated、revoked。
来源：安全评审 `🔴`。

8. 必须建立敏感数据分类、加密、脱敏与第三方处理边界。
修改要求：对账号标识、语音、转写文本、练习结果、共享信息明确落盘策略、传输加密、日志脱敏和第三方 TTS/ASR 数据处理规则。
来源：安全评审 `🔴`。

9. 必须补 API 防滥用策略。
修改要求：限流、防刷、nonce/幂等键、重放防护、CORS allowlist、需要 cookie 的入口启用 CSRF token + SameSite。
来源：安全评审 `🔴`。

10. 如果产品涉及儿童语音、成长记录或家庭数据，必须补隐私合规设计。
修改要求：家长同意、最小必要采集、删除权、导出权、第三方处理清单、留存矩阵和再利用评估流程。
来源：安全评审 `🔴`。

## 确认合理的设计决策

1. 以 Riverpod/Notifier 统一状态主栈，而不是继续容忍双真相源，是正确的根因级选择。
2. 保留模块化单体、暂不拆服务，符合当前问题结构和团队承载能力。
3. 将 app 层收口为 composition root，有助于降低根部热点与并行开发冲突。
4. 用 shared contracts（TypedRouteArgs、ViewState DTO、ErrorEnvelope）收口跨模块边界，方向正确。
5. 将动态无障碍能力抽到统一服务层，而不是分散在页面实现，是提升一致性的合理设计。
6. 采用 quick pack + nightly + pre-release 的三层门禁思路，符合当前团队效率与风险控制平衡。
7. 里程碑顺序按“先边界与护栏，再状态迁移，再体验重构，最后清理闭环”展开，是合理的交付节奏。
8. 明确“不重写产品，而做增量式重构”的总体策略，是当前最现实的路径。
